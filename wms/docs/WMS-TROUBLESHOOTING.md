# WMS LOGOFF — устранение неисправностей

## 1. Правило диагностики

Сначала зафиксируйте:

- точное время по Москве;
- логин и роль;
- клиент;
- раздел;
- номер заявки, заказа, короба, ШК или КИЗ;
- полный текст пользовательской ошибки;
- последнее успешное действие.

Не исправляйте остатки «на глаз» до сохранения этих данных.

## 2. HTTP 502

502 означает, что Nginx не получил корректный ответ API/web upstream.

Проверка на VPS:

```bash
cd /opt/logoff-wms/wms/infra
docker compose ps
docker compose logs --tail=200 api
docker compose logs --tail=100 nginx
curl -i http://127.0.0.1/api/v1/health
df -h
free -h
```

Ищите:

- container exited/restarting;
- TypeScript/runtime error после развёртывания;
- Prisma connection error;
- PostgreSQL max connections;
- нехватку памяти или диска;
- долгий запрос и timeout.

Перезапуск — не диагноз. Если после перезапуска ошибка возвращается, сохраните логи и найдите конкретный запрос.

## 3. WMS тормозит

1. Откройте логи API и найдите длительность запросов.
2. Проверьте, не запущены ли одновременно несколько тяжёлых WB-синхронизаций.
3. Проверьте интервалы auto-refresh.
4. Проверьте PostgreSQL locks и active queries.
5. Проверьте размер ответа: КИЗы и группы должны быть свёрнуты.
6. Проверьте индексы фильтров clientId/status/createdAt/boxId/skuId.
7. Проверьте свободную память и swap.

Четырёх ядер и 6 ГБ достаточно для умеренной нагрузки при пагинации, индексах и отсутствии N+1.

## 4. Не входит пользователь

- Убедитесь, что status пользователя ACTIVE.
- Проверьте раскладку и регистр логина.
- Проверьте maintenance mode.
- Проверьте, что demo-пользователь не пытается войти в live-контур.
- Сбросьте пароль через модуль доступов, не через прямой SQL.

## 5. Плитка не видна

Проверьте по порядку:

1. требуемую роль/permission;
2. client-only audience;
3. feature flag клиента/логина;
4. персональное скрытие в «Администрирование → Видимость»;
5. для «Администрирование» — owner allowlist.

После изменения обновите сессию или подождите не более пяти секунд серверного cache TTL.

## 6. Короб не найден

- Показать пользователю номер короба и понятное «в системе его нет».
- Проверить регистр и автоисправление префикса.
- Искать в активных остатках и архиве.
- Проверить clientId: один номер нельзя путать между клиентами.
- Проверить историю перемещений и паллет-размещение.

Технический текст `WMS HTTP 404` не должен показываться оператору.

## 7. Короб уже проверен

Повторная инвентаризация запрещена, пока администратор не разрешит повторную проверку. Не удаляйте успешную историю ради новой проверки. Создайте разрешение/новую сессию с ссылкой на предыдущую.

## 8. Инвентаризация показала «всё ОК», но товара нет

1. Откройте строки проверки, а не только заголовок сессии.
2. Сравните expectedQuantity и countedQuantity каждого SKU.
3. Проверьте, что сканировался ШК, а не КИЗ.
4. Проверьте агрегацию одинаковых ШК/вариантов.
5. Убедитесь, что пустой counted result не был ошибочно заменён expected.
6. До актуализации сохраните снимок состава.

## 9. Заявка не видна на ТСД

- статус должен допускать сборку;
- заявка должна быть синхронизирована/опубликована для ТСД;
- устройство не должно держать чужую незавершённую сессию;
- фильтр ТСД не должен автоматически открывать только первую заявку;
- заявка должна содержать положительные незавершённые строки.

Используйте кнопку синхронизации и затем обновите список заявок, а не APK.

## 10. ТСД пишет «короб не нужен»

Проверьте:

- короб содержит SKU хотя бы одного незавершённого заказа;
- резерв не закреплён ошибочно за другим заказом;
- один короб не заблокирован целиком;
- переклейка применяется только при отсутствии целевого остатка;
- заявка актуальна после изменения FBS-группы.

Если короб нужен позже в этой же заявке, WMS должна начать работу с ним сейчас.

## 11. КИЗ не найден или не соответствует

Возможные причины:

- товар принимался без КИЗа;
- КИЗ числится в другом коробе;
- конкретная метка уже зарезервирована;
- отсканирован КИЗ другого SKU;
- GS1-строка нормализована иначе.

Безопасные действия:

1. подтвердить товар по ШК/SKU;
2. проверить, что КИЗ не использован в завершённом заказе;
3. если он числится в другом коробе — предложить фактическое перемещение;
4. если SKU совпадает и метка новая — привязать к фактической единице с audit;
5. сохранить КИЗ в заявке.

Нельзя просто отключать проверку уникальности КИЗа.

## 12. Недостаточно товара при закрытии заявки

1. Пересчитать текущий остаток и уже списанное количество.
2. Проверить выбранные короба.
3. Показать оператору короба с доступным товаром.
4. Разрешить указать фактический короб.
5. Если товар реально был без короба — выбрать «Без короба» с причиной.
6. Не списывать ниже нуля.

«Товар уже готов» не заменяет источник списания; WMS должна сохранить факт, откуда его взяли.

## 13. FBS-заказы не обновились

- Запустите диагностику подключения.
- Проверьте срок токена и доступ к orders.
- Проверьте выбранный склад WB.
- Запустите sync для правильного клиента.
- Проверьте lastSyncAt и сообщение последней ошибки.
- Сопоставьте order ID WB с локальным order ID.
- Обновите резервы после отмен и переносов.

## 14. Нет грузомест WB

Проверьте тип сдачи. Для СЦ и ПВЗ правила могут различаться. Локально отсканированный физический короб ещё не означает созданное грузоместо WB. Нужны вызов API создания/обновления поставки и сохранённая связь с WB supply ID.

Перед завершением покажите reconciliation:

- локальные короба;
- локальные товары;
- WB orders;
- WB cargo places;
- отсутствующие связи.

## 15. Неверные резервы FBS

Кнопка обновления должна:

1. получить текущие активные/отменённые статусы;
2. освободить отменённые и архивные;
3. исключить завершённые;
4. пересчитать только незавершённые количества;
5. не резервировать один КИЗ дважды;
6. записать summary.

## 16. Ошибка биллинга

- Определите источник charge.
- Проверьте тариф, дату действия и налог.
- Проверьте turnkey FBS.
- Проверьте idempotency source/sourceId.
- Сравните количество фактически отгруженных единиц.
- Не удаляйте проведённое начисление; используйте корректировку.

## 17. Восстановление

Перед восстановлением определите, нужен ли rollback приложения или данных.

- Ошибка интерфейса/кода: верните предыдущий образ.
- Неверная настройка: восстановите прежнее значение из AuditLog.
- Повреждение данных: остановите запись, создайте текущий аварийный дамп, затем восстанавливайте проверенную резервную копию в отдельную БД и сравнивайте.

Никогда не восстанавливайте production вслепую поверх текущей базы.
