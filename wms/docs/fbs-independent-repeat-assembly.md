## Пользовательский сценарий

FBS → Отгруженные → отметить заказы → «Проверить для повторной сборки».
Предпросмотр показывает исходные заявки/поставки, товары, короба и паллет-сорты.
После проверки менеджер с ролью ADMIN/OWNER подтверждает дополнительный физический
расход и создаёт отдельную заявку IN_WORK. Доступ к клиенту и филиалу проверяется
на сервере. Проверка доступна для 1–100 поштучных заказов одного кабинета WB.

WB проверяется адресно через существующий ограничитель запросов, без общего
обновления клиента. Разрешено только подтверждённое WB `complete/waiting` и
завершённая предыдущая попытка WMS. Отменённые, неизвестные, уже доставленные и
собираемые другим сотрудником заказы блокируются. Данные перепроверяются при
подтверждении. Недостаток остатков отменяет создание всей заявки.

## Что сохраняется

- Полный снимок прежней сборки и её связи с исходной заявкой записывается в
  `FbsAssemblyAttemptHistory` до изменения текущего задания.
- У новой попытки новый UUID. Прежние `fbs-sticker-pick:<id>` и уникальный
  `ShippedKizHistory.assemblyId` остаются ключами только предыдущей попытки.
- Создание заявки не создаёт/не отменяет движений товара, не возвращает прежние
  КИЗ в AVAILABLE, не удаляет печать, выработку и позиции старой заявки.
- Количество в исходной заявке сохраняется и при последующей синхронизации WB.
- ФОТ, мониторинг, счётчик ТСД, история наклеек, онлайн-факты, список заявок и отчёт
  «Упаковка FBS» читают обе физические попытки с исходными датами/сотрудниками.
- Для новой попытки допускается одна новая запись печати того же заказа.
  Один КИЗ по-прежнему нельзя использовать повторно. Старую наклейку можно
  просмотреть/перепечатать через сохранённую историю.
- В WB не создаются новые заказы/поставки и не перезаписываются КИЗ/статусы.
  Повторная сборка использует существующий аварийный режим WMS.

## Надёжность

Создание выполняется одной SERIALIZABLE-транзакцией. Состав старых попыток входит
в уникальный fingerprint операции. Повторное подтверждение возвращает существующую
заявку. Параллельные операции дополнительно защищены advisory lock и проверками
`id + updatedAt` при замене текущей сборки и связи. Любой конфликт прерывает
транзакцию. Обычное обновление WB не добавляет в повторную заявку посторонние
заказы из исходных поставок и сохраняет пояснение о дополнительном расходе.

Распределение учитывает клиентский режим остатков (паллет-сорт/короба), филиал,
положительные AVAILABLE-остатки, действующие резервы и соответствия артикулов
с совпадающим размером. Сопоставление не выделяет одну физическую единицу дважды.

Ограничения первой версии:

- Старые попытки с `cargoPackingId` блокируются: повторная упаковка уже
  зарегистрированных грузомест требует отдельной реализации.
- Если в одном коробе для одной целевой позиции выбраны разные исходные SKU,
  создание блокируется, так как существующая детализация отборов имеет ключ
  «позиция + короб», без отдельного исходного SKU. Нужно разделить такие заказы.
- Снимки прежних попыток являются историческими фактами, не текущими заданиями.
  Прямые операции, требующие действующего assemblyId, не должны применяться к ним.

## Включение и остановка

`WMS_FBS_REPEAT_ASSEMBLY_ENABLED` по умолчанию отсутствует:
нет новых запросов к архивным таблицам, повторная сборка недоступна.

Только в нашей WMS после резервной копии, миграции, проверки и согласованной выкладки:

- `true` — создание повторов и чтение истории;
- `read-only` — запрет новых повторов, но сохранение чтения истории, статистики,
  резервов и печати уже созданных попыток.

После создания первой повторной попытки **нельзя** просто удалить флаг,
возвращать старый бинарник или восстанавливать уникальный индекс только по
`orderId`: это скроет историю в старых читателях/нарушит новую уникальность печати.
Для остановки использовать `read-only`; возврат старой модели требует отдельного
плана миграции без потери фактов. На проданной WMS миграцию/флаг не включать.

## Выпуск и остановка

Перед переключением сверить текущий image и хэши исходников с manifest, сохранить
текущий контейнер/образ для восстановления, применить только данную миграцию
с ON_ERROR_STOP. Старые незарегистрированные миграции автоматически не запускать.
Проверить каталог pg_indexes и наличие новой уникальности. Затем переключить только API
с `WMS_FBS_REPEAT_ASSEMBLY_ENABLED=true` и проверить health/старт без ошибок.
Создание выполняется штатным сервисом после свежего адресного ответа WB, с аудитом.
Не отправлять WB-мутации из операционного скрипта и не заменять настоящую авторизацию.

До первой повторной заявки возврат старого образа безопасен; новые пустые таблицы
можно оставить. После первого повтора старый образ не возвращать: для остановки
новых повторов установить `read-only`, сохранив читателей истории и учёт расхода.
