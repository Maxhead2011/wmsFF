# Подозрительные ШК приёмки

Статус: реализация в `fix/receipt-suspicious-barcode-review`, для PR в `feature/wb-print-check`. Не опубликовано. Production-флаги и остатки этой работой не изменены.

## Поведение

- В LOGOFF ТСД неизвестный/необычный ШК требует двух одинаковых вводов. `18`, `7459`, `08123282` требуют повторного скана. Если сканы различаются, следующий ввод должен подтвердить последний ШК. Есть отмена текущего скана. Два совпавших скана добавляют одну единицу.
- Проверка формата: неизвестные коды короче 12 или длиннее 14 цифр, нецифровые значения, неверная контрольная цифра. Известная недрафтовая карточка на сервере считается допустимой, включая внутренний короткий ШК. ТСД просит повторить короткий код и для известной карточки; сервер принимает его штатно.
- API до создания SKU/движения сохраняет неизвестный подозрительный ШК как `TsdOperation: NEEDS_REVIEW`. Старые ТСД также защищены сервером, но вместо второго скана в обращении будет «Не передан старой версией ТСД».
- Короб можно закрыть и продолжить приёмку. В подтверждённое количество не входят ожидающие/отклонённые позиции. Нельзя переиспользовать закрытый короб с ожидающими обращениями. Повтор операции не создаёт второй приход.
- Администрирование → Проблемы приёмки → Подозрительные ШК: клиент, короб, приёмка, оба скана, количество, оператор/устройство, время МСК, причина и решение.
- ADMIN/OWNER с правом изменения выбранного филиала и клиента могут подтвердить ШК, исправить на существующий ШК этого клиента либо отклонить. Обязательное основание и проверка физического товара в интерфейсе. Исправление маркируемого товара сохраняет обычную обязательность КИЗ.
- Решение, приход, изменение статуса обращения и аудит выполняются одной Serializable-транзакцией с блокировкой обращения. Повторное решение отклоняется. Обычный старый обработчик ТСД не позволяет обойти этот разбор.
- Сначала выводятся ожидающие обращения, затем решения за последние 7 дней, максимум 200 записей. Счётчик использует отдельный запрос без загрузки всей истории.
- Администратору доступен ограниченный раздел разбора без запросов к настройкам собственника. Пункт «Проблемы ФБО» проверяет существующий серверный capabilities; ошибка загрузки приёмки не отключает ФБО.

## Изоляция и файлы

API: `receipt-barcode-policy.ts`, `receipt-barcode-review.service.ts/controller.ts`, `tsd-sync.service.ts`, `tsd-review.service.ts`, `tsd-receipt.service.ts`, `tsd.module.ts`, реестр `administration-internal-api.service.ts`.

Общий `StockOperationsService.receiveIntoBox` получил необязательную внешнюю транзакцию и тип движения; старые вызовы используют прежнюю транзакцию и RECEIPT. Новая ветка активируется только флагом `WMS_RECEIPT_BARCODE_REVIEW_ENABLED=true`.

Web: `ReceiptBarcodeProblems`, `OperationalProblemsPanel`, `AdministrationPanel`, `workspaces.ts`, API-обёртки и локальные стили. Флаг `VITE_ADMIN_PROBLEMS_ENABLED=true`. `AdministrationFboProblems.tsx` и стили восстановлены из существующего проверявшегося release-кандидата `work/fbo-problems-release/candidate`; бизнес-логика серверного ФБО не меняется.

Android: `MainActivity`, `ReceiptBarcodeRescan`, `OperationOutbox`, `TsdSyncRunner`. Повторный скан и продолжение очереди после NEEDS_REVIEW только в flavor `logoff`; `ffullhab` сохраняет прежнее поведение. Версия APK пока не повышена: это изменение исходников, а не выпуск.

## Четыре исторические записи

`src/scripts/stage-suspicious-receipts.ts` выбирает только четыре кода коробов `FFL_LKB0610_038`, `132`, `235`, `315` с ожидаемыми ШК 07.10.2026 (МСК), по одной единице. Требует явные ID клиента, филиала и активного OWNER.

```
node dist/scripts/stage-suspicious-receipts.js <clientId> <warehouseId> <ownerId> --dry-run
node dist/scripts/stage-suspicious-receipts.js <clientId> <warehouseId> <ownerId> --apply
```

Пробный запуск выполняет ту же транзакцию и откатывает её. Применение — только после публикации API/UI и проверки пробного отчёта. При изменившемся остатке, других движениях либо КИЗ операция останавливается. Оригинальный приход остаётся в истории; парные движения AVAILABLE → BLOCKED исключают спорную единицу из доступного остатка. Решение разбора снимает блокировку через INVENTORY_ADJUSTMENT, не создавая повторный RECEIPT. Повтор импорта идемпотентен. В production скрипт ещё не запускался.

## Проверки

- Регрессионный тест закрытия короба запущен на исходном `HEAD`: падает с RETRY вместо APPLIED. На исправлении проходит.
- Новые API-тесты: классификация ШК, права, филиал/клиент, старый APK, повторное/конкурентное решение, коррекция, отказ, откат, запрет обхода старым обработчиком, защита переиспользования, исторический карантин и ограниченный список.
- Web: ADMIN/OWNER и sold-флаг; headless Edge проверяет реальный интерфейс, обязательную отметку, одну отправку решения, независимость ФБО от ошибки приёмки и отсутствие фоновых owner-only запросов. Все HTTP в браузерном тесте — фиктивные.
- Android: повтор, несовпадение, отмена/смена короба, очистка доказательств, очередь более 50 сканов с NEEDS_REVIEW; проверены LOGOFF и ФФУЛЛ-ХАБ.
- TypeScript API проверяется с изолированно сгенерированным Prisma из текущей схемы (общий node_modules содержит устаревший клиент); TypeScript web проверяется штатно.
- Интеграции PostgreSQL без выделенной тестовой БД не подтверждены. Старый `kiz-duplicate.integration.spec.ts` падает при отсутствии URL ещё при создании PrismaClient, до skip; исключён из общего повторного запуска, прочие штатные пропуски отражены в отчёте. Сам тест не изменён.

Итоговый общий прогон: API 3204 passed, 141 skipped (9 файлов; отдельно исключён один описанный выше DB-файл); web 408 passed, 2 skipped. Сборки тестов Android обе успешны. Headless Edge — PASS. Пропуски не считаются успешными проверками.

## Публикация

Соблюдать `release-workflow.md`: `sourceParityVerified=false`, поэтому полная локальная сборка не заменяет production. Перед выпуском сверить свежий runtime и подготовить ограниченный delta. Существующий production FBO backend не представлен в текущей исходной базе целиком; его capabilities/политику ADMIN проверять на кандидате, не заменять серверную реализацию.

Порядок: API с выключенным флагом → проверка delta/здоровья → web → включение флагов только нашей WMS → новый подписанный LOGOFF APK с новым versionCode → пробный перенос четырёх исторических записей → отдельное применение. Проданную ВМС и её флаги не менять.
