# Проверка статусов WB на экране FBS

Подготовлено локально 17.11.2026. Публикация не выполнена.

Рабочий `listFbsOrdersForDisplay` обновляет выборку через `historyMode: active-only`.
После передачи заказа WB исключает его из `/orders/new`. Объединение с прежним
операционным кэшем возвращало старую строку `new`, поскольку новый ответ уже
не содержал этот номер. Ветка Git не содержит этот метод рабочего сервера,
поэтому выпуск требует точечного наложения на свежий runtime.

`fbs-display-wb-reconcile.ts` сверяет отсутствующие в свежей выборке активные
строки WB через `/orders/status`. Кабинеты проверяются в области текущего клиента,
пакеты ограничены 1000 номерами. Категория и подпись рассчитываются существующими
функциями рабочего сервиса. Подтверждённые строки входят в новый снимок и заменяют
старые строки при объединении кэшей. Ошибка или неполный ответ WB оставляет
последний успешный снимок и выводит ошибку фоновой синхронизации.

Изменение подключается только в метод чтения экрана нашей WMS. Подготовка
не вызывает сборку, передачу, тарификацию или обновление заявок. Проданная WMS
не входит в кандидат. Обычная полная сборка TypeScript не заменяет runtime.

## Состав кандидата

- `modules/marketplace-connections/marketplace-connections.service.js` — одна замена callback фонового обновления.
- `modules/marketplace-connections/fbs-display-wb-reconcile.js` — компилируемый модуль сверки.

`scripts/releases/fbs-stale-wb-status/prepare.py` принимает свежий опубликованный
сервис, скомпилированный модуль и выходной каталог. Скрипт проверяет единственность
точки подключения и сохраняет SHA256 исходного и изменённого сервиса. Команд
публикации в нём нет. Перед будущим выпуском обязательны свежая сверка runtime,
проверка состава всего кандидата и отдельное разрешение пользователя.

## Проверки

`runtime.test.cjs` исполняет настоящие методы `listFbsOrdersForDisplay`,
`mergeIncrementalFbsOrders` и классификацию рабочего модуля с адаптерами сети,
кэша и проверки области клиента. Проверяется второй запрос экрана после
завершения фонового обновления. Базовый модуль воспроизводит регрессию.

Запуск после компиляции helper и подготовки кандидата

```powershell
$env:FBS_RUNTIME=(Resolve-Path work/candidate/marketplace-connections.service.js).Path
$env:FBS_LIVE_PROOF=(Resolve-Path work/live-proof.json).Path
node --test wms/scripts/releases/fbs-stale-wb-status/runtime.test.cjs
```

17.11.2026 в 15:08 МСК получены свежие официальные статусы восьми заказов
6288167909, 6288207188, 6288210468, 6288316060, 6288399127, 6288435315,
6288438753, 6283746839. Все имеют `complete / sorted`. Заявки 3090 и 3099
в рабочей БД имеют `DONE`. Локальный прогон этих ответов через метод кандидата
оставил ноль активных строк и сохранил статусы каждого заказа согласно WB.
Это проверка кандидата с реальными ответами API. Проверка опубликованного
интерфейса после изменения возможна после разрешённого выпуска.

Технические доказательства хранятся локально в `work/` рабочей ветки.

Итог проверки кандидата — 7/7, включая повторное обновление и восемь реальных
ответов WB. Строгая компиляция нового TypeScript-модуля и синтаксическая проверка
обоих файлов кандидата проходят. SHA256 опубликованного сервиса повторно совпал
с базой перед проверкой.

Общие проверки — API 4820 тестов прошли, 181 пропущен; web 644 прошли,
2 пропущены. Проверки, первоначально не запустившиеся из-за рабочего каталога
и поиска TypeScript, повторно прошли в каталогах приложений. Отдельный API suite
`kiz-duplicate.integration.spec.ts` не загрузился, поскольку отсутствует
`KIZ_DUPLICATE_TEST_DATABASE_URL`, а его конструктор Prisma исполняется ещё до
пропуска suite. Полный API-прогон поэтому имеет ненулевой код завершения.
Этот тест не относится к изменённому пути чтения FBS.

health, окружение и идентификаторы остальных контейнеров.
