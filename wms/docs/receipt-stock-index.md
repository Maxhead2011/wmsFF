# Индекс доступности приёмок

Связь короба с приёмкой хранится в `ReceiptStockIdentity`. Остатки, резервы и
стоимость хранения остаются в прежнем учёте. Триггеры обновляют связь вместе с
приёмкой, исправлением, удалением или изменением принадлежности короба в одной
транзакции. Подтверждение клиента и явное назначение приёмки читаются актуальными;
кэш с задержкой обновления не используется. Отсутствующий индекс запрещает отбор.

`receiptRules` и `pendingReceiptBoxIds` используют индекс при
`WMS_RECEIPT_STOCK_INDEX_ENABLED=true`. Значение по умолчанию — выключено;
включение предусмотрено только в нашей ВМС после миграции
`20261008120000_receipt_stock_identity`. Проданная ВМС не обновляется.

ФБО рассчитывает маршрут оставшегося спроса. При полностью отобранном спросе
или упаковке новый путь не загружает доступность и маршрут. Часть оптимизации
упаковки уже присутствовала в production и сохранена. Постоянного кэша маршрута
нет: действующие резервы должны учитываться. Начатые задания ФБС не перераспределяются.

## Проверки

- `receipt-stock-index.spec.ts`: история не читается; актуальное подтверждение,
  отмена подтверждения, направление и принадлежность, блокировка и изоляция.
- `fbo-remaining-plan.spec.ts`: только недостающие позиции; пустой спрос,
  упаковка, завершение и выключенный флаг. Четыре теста воспроизводили проблему до исправления.
- `scripts/tests/receipt-stock-index.sql`: отдельный PostgreSQL, миграция,
  изменения и удаления источников, откат. Проверены два одновременных поступления.
- `scripts/tests/receipt-stock-index-runtime.cjs`: сравнение старого и нового
  пути на одном снимке, обязательный откат, без сканирования и списания товара.

Последний предпубликационный замер: план ФБО 6352 → 2203 мс, проверки доступности
короба ФБС 36–84 → 5–7 мс. Совпали 319 недоступных коробов, 1421 правило и весь
план заявки. Это серверные компоненты, без камеры, сети и внешнего API WB.

## Выпуск и откат

Только три runtime-модуля накладываются на проверенный production baseline:
`warehouse/receipt-stock-index`, `warehouse/receipt-channel-policy`,
`tsd/fbo-two-stage.service`. Полная локальная сборка не публикуется.
Миграция выполняется атомарно, затем включается флаг и проверяется реальный индекс.
При ошибке возвращаются прежний API и конфигурация. Дополнительная таблица может
остаться: прежний код её не читает; физические остатки миграция не изменяет.
