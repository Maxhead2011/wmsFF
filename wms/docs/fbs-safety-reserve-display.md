# Страховой резерв в таблице FBS WB

Подготовлено в `fix/fbs-safety-reserve-display`, целевая ветка PR — `feature/wb-print-check`. Не опубликовано.

Таблица ранее показывала доступность до страхового резерва, хотя публикация в WB
вычитала его. Теперь резерв заказов и страховой резерв показаны отдельно, а
`sellable` и сумма «Доступно к продаже» учитывают эффективное правило плана.
Пример: 10/26/89 при резерве 3 дают 7/23/86, всего 116 вместо 125.

Изменены только ответ `buildFbsStocksResponse`, помощник отображения, тип ответа
и колонки `FbsPanel`. Публикация остатков, записи резервов, движения и настройки
не изменяются. `NONE` для уже обработанного общего пула не вычитает резерв повторно.

## Проверки

- Регрессионный тест до исправления: отсутствует `safetyReserve`, возвращаются 10/26/89.
- После исправления: 3 теста ответа/правил, включая управляемые и не настроенные товары,
  малый остаток, округление процентов, ограничение нулём и индивидуальные правила.
- Общие API: 3295 прошли, 150 пропущены; отдельный `kiz-duplicate.integration.spec.ts`
  исключён, как в базовом прогоне. Дополнительные DB-тесты требуют отдельного окружения.
- Общие web: 416 прошли, 2 пропущены. TypeScript API (изолированный Prisma) и web прошли.
- Фактический candidate runtime: 17 проверок, включая FBS capability, Ozon,
  последовательный отбор WB и отдельную печать целевого ШК.
- Browser test использует ответ настоящего candidate-сервиса, проверяет две колонки,
  строки 7/23/86, итог 116, отсутствие ошибок JS и запросов изменения данных.

## Подготовка выпуска

База `2026-10-10-marketplace-links`, сверена с живыми образами 10.10.2026:
API `sha256:86507fac72559b74a63b39a706ca15004286cd9d1e94f0868907dae15b3132a4`,
web `sha256:713de0c036bf3f11c496df4ba14d59341de7821a1543734c28b7711020d655ff`.

`sourceParityVerified=false`: исходный расчёт плана не содержит всех действующих
дополнений страхового резерва. Поэтому помощник читает эффективные `reserve` и
`skuRules` существующего runtime-плана; отсутствие правила означает нулевой резерв.
Полная сборка исходников не является артефактом для публикации.

После `release_baseline.py materialize` применить `build-reserve-display.cjs`
к новому каталогу API и текущему графу web. Скрипт меняет только поле ответа внутри
нужного метода, добавляет помощник и две колонки; сохраняет единственный React.
`check-candidate` подтвердил изменения только двух API-файлов:
`marketplace-connections.service.js` и `fbs-stock-reserve-display.js`.
Перед публикацией повторно сверить базовые image ID и выполнить обычный PR-процесс.
