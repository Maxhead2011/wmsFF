# Подтверждение найденной единицы после исчерпания исходного остатка

Подготовлено 30.10.2026. **Не опубликовано.** Ветка `fix/inventory-found-kiz-review`, целевая интеграционная ветка `feature/wb-print-check`.

## Причина

В №2371 при отборе был зарегистрирован новый КИЗ, отсутствовавший среди пяти КИЗов приёмки. Его отбор израсходовал количество исходного короба, оставив другой принятый КИЗ AVAILABLE при нулевом остатке. Позднейший физический пересчёт подтвердил этот прежний КИЗ в другом коробе. Обычный перенос справедливо остановился на попытке списать единицу из пустого источника.

## Изменения

- `fbo-known-kiz.ts / requireKnownFboKiz`: неизвестный КИЗ требует разбора приёмки, автоматическое создание при отборе запрещено. Исторические отгрузки не переписываются.
- `found-unit-review.ts / confirmFoundUnit`: отдельный POST `/inventory/boxes/:id/found-unit` для ADMIN/OWNER с причиной, повторным вводом КИЗа и явным подтверждением. Проверяются права на клиента/филиал, завершённый свежий пересчёт, сохранённый скан, единственность марки, нулевой источник, уже учтённое целевое количество, резервы/сборки, история отгрузок и изменения после скана.
- Привязка меняется в Serializable-транзакции с блокировкой идентичности/коробов, сравнением версии марки и постоянной записью результата. Повтор запроса не создаёт движения. Количество не меняется. Эта операция не завершает весь пересчёт; после разбора всех блокировок используется штатная актуализация.
- `confirmed-kiz-transfer.ts`: ошибка называет фактический исходный короб, КИЗ, наименование, артикул и размер.
- `unlockTsdInventory`: освобождение ТСД переводит BOX_CHECK в REVIEW вместо CANCELLED. Частичные сканы остаются частичными: COUNTING не выдаётся за завершённый пересчёт. Полная инвентаризация сохраняет прежнее поведение.
- `FoundUnitConfirmation.tsx`: форма в текущей проверке, доступность по серверной capability. Старые отменённые проверки автоматически не открываются.

## Изоляция и выпуск

Новый флаг `WMS_INVENTORY_FOUND_UNIT_ENABLED` по умолчанию выключен. Включать только в нашей WMS после публикации проверенных API/web. Проданная WMS, APK, схема и бизнес-записи этим изменением не затрагиваются. Более информативная ошибка использует существующий флаг переноса КИЗ.

Фактически прочитанная база 30.10:

- API `sha256:a6869f7a212a8d34a9a7998ed3c86f17d21b6d3f8af0b741d0a2e2fc31691cb2`.
- Web `sha256:1337bf9d6d252aee214d58220380529a0dd6d0a8ec9054938d0013b2fca7f185`.
- `sourceParityVerified=false`. В опубликованном `bindPickedMark` есть восстановление/создание марки, отсутствующее в локальном TS. `scripts/patch_fbo_known_kiz.py` добавляет ровно один вызов проверки после поиска марки в копии этого модуля, требует SHA256 входного файла и запрещает перезапись источника. Для выпуска необходим соседний скомпилированный `fbo-known-kiz.js`.
- Полная локальная сборка не является кандидатом для публикации. Перед выпуском повторно снять актуальную базу и подготовить точечный runtime delta остальных затронутых модулей по release-workflow.md. Публикация в рамках этой задачи не выполнялась.
