# Довоз для урегулирования потерь ПВЗ

Отдельный режим в «Сервис → Повторная сборка со старым стикером». Администратор или собственник выбирает клиента, вводит прежний номер заказа WB, включает режим и указывает основание. После проверки отдельно подтверждает дополнительный расход.

Новая заявка имеет высокий приоритет. Сохраняется исходная этикетка WB. Отмена заказа допустима только в этом режиме при подтверждённой прежней отгрузке. Проверки обычной повторной сборки сохраняются.

## Доказательства и склад

- WB, один прежний заказ и точная попытка, доступный клиент и рабочий филиал.
- WbOrderShipment должен совпасть по клиенту, кабинету, заказу, попытке, заявке, складу, SKU и количеству. Для маркированного товара требуется прежний КИЗ в снимке отгрузки.
- Прежняя попытка архивируется с исходными значениями. Старый RELEASED-снимок дополняется доказательством отгрузки; чтение не меняет его статус или КИЗ.
- Новая попытка получает новый идентификатор и пустые физические сканы. Товар и новый КИЗ учитываются при реальном отборе действующим складским механизмом. Старые списания не отменяются.
- Без свободного точного товара создаётся WAITING_STOCK. Неподтверждённая замена модели запрещена. Учитываются действующие резервы и размещение клиента.
- Печать закреплена за проверенной исходной этикеткой. Создание идемпотентно, сериализовано и защищено CAS.

## Очередь и синхронизация

Сервер создаёт защищённую запись SystemSetting `fbs.pvzLossSettlement.<requestId>` с purpose, клиентом, складом, новой попыткой, заказом и доказательством прежней отгрузки. Исключение из терминальных фильтров действует только для совпадающего контекста. Заголовок или комментарий не предоставляют это право.

ТСД показывает локальную сборку с фактическими supplierStatus/wbStatus. Обновление маркетплейса освежает эти поля, но не отменяет и не завершает довоз автоматически. КИЗ и статусы заказа в WB не меняются. Действующие проверки товара, источника и КИЗа сохранены. Закрытые заявки и удалённые связи не восстанавливаются.

## Изоляция и выпуск

`WMS_FBS_PVZ_LOSS_SETTLEMENT_ENABLED=true` включается только в собственной WMS. По умолчанию выключен. Требуются действующие флаги повторной сборки и первоначальных стикеров. Проданная WMS не обновляется. Схема БД не меняется.

Source/runtime parity=false: выпуск меняет только проверенные участки актуального runtime, с обратной проверкой сохранённых байтов. API5/web2; полной замены сервиса нет. Основной web-модуль и его алиасы переключаются вместе, чтобы страница не запускала две версии.

## Проверки

Регрессия создания отменённого RELEASED-заказа воспроизведена до исправления. Unit-тесты проверяют точное доказательство, область доступа, выключенный режим, дефицит, сохранение отмены и снимка. Runtime12 проверяет собранную очередь, сканирование и синхронизацию. Изолированный PostgreSQL8 проверяет параллельное создание, прежний стикер, новый КИЗ и однократное перемещение в PACKING без изменения старой отгрузки. Браузер проверяет реальный bundle панели, основание, подтверждение, дефицит и смену клиента. Дополнительно проверены запуск/обновление страницы с одним основным модулем и загрузка ФБС.

API4660/web622 passed; 9/2 skipped, dedicated DB integration suites excluded. Отдельный PostgreSQL-сценарий нового режима прошёл. Web TypeScript прошёл; общий API TypeScript имеет прежние ошибки сгенерированных типов Lamoda, в изменённых файлах ошибок нет.

Физический отбор новых единиц выполняют сотрудники. Создание заявок не означает, что товар уже отобран или передан.

Priority follow-up: verified PVZ requests appear alongside the ordinary fixed five in the worker list; direct selection uses the same exact-purpose proof. Ordinary window membership is unchanged.

## Адресный допуск из приёмки на согласовании — подготовлено

Общее согласование приёмки сохраняется. Для подтверждённого собственником довоза можно записать серверный `receiptSourceApproval` в уже существующее доказательство назначения заявки: точные task/box/SKU, количество строго 1, автор, время и основание. Проверяются клиент, филиал, состояние короба и действующее назначение довоза. Другие заявки, ФБО и общая публикация остатков этим разрешением не пользуются.

В очереди и при подтверждении короба допуск проверяется заново. Маршрут показывает фактический короб без выдуманного палет-сорта; доступность учитывает текущий остаток и конкурирующие резервы. Завершённое задание больше не использует допуск. Обязательные сканы товара и КИЗа, прежний стикер, однократное физическое списание и обычные проверки сборки сохраняются. Данные допуска и резерв одной единицы применяются отдельной аудируемой транзакцией после выпуска кода.

Поправка изолирована существующим флагом режима довоза нашей WMS. API3/web0 накладывается на актуальные серверные файлы; обратная проверка подтверждает сохранение остальных байтов. Регрессия: 17 новых проверок, целевой набор51; API4677/9 skipped, интеграционные наборы отдельной БД исключены. Проверены реальные данные в транзакции с откатом: маршрут и экран SCAN_BOX, приёмка остаётся на согласовании, товар/КИЗ/прежняя этикетка не изменены.
