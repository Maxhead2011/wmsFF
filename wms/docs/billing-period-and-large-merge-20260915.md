## Причины и изменения

1. Веб передавал сотни UUID счетов в GET URL предварительного объединения FBS.
   Подтверждено на сервере: 438 UUID образовали URL 17 179 байт, Node вернул 431,
   публичный nginx — 414. Клиент показывал `Failed to fetch`.
   Теперь выбранные UUID передаются одним POST JSON. Старый GET сохранён.
   Новый DTO проверяет непустой clientId, UUIDv4, уникальность и максимум 10 000 ID.
   Отсутствующий invoiceIds сохраняет прежний режим всех доступных счетов;
   явно пустой/null список отклоняется, а не расширяется до всех счетов.
   Разрешение billing:read, проверка клиента/филиала и сервис предпросмотра прежние.

2. Фильтр исключения Лукина по умолчанию исключал даже явно выбранного клиента.
   Теперь исключение относится только к массовому расчёту; при конкретном клиенте
   флажок отключён, снят и сопровождается пояснением. При возврате ко всем клиентам
   прежняя настройка массового исключения сохраняется.

3. Классификатор периода пропускал восстановленные FBS-счета, содержащие одновременно
   FBS и первичную/дополнительную обработку. Теперь распознаются только доказанные
   документы клиента 0001 с completed-work sourceKey и сохранённым маркером
   FBS_COMPLETED_WORK_V1 / processingOnly. Сформированный из них FBS-счёт за период
   также распознаётся по точному sourceKey операции и происхождению начислений.
   Повторный расчёт видит уже существующий счёт. Строгий классификатор произвольных
   смешанных документов не изменён.

Цены, налоги, количества и ссылки на начисления копируются без пересчёта.
Сохраняются проверки неоплаченного черновика, дублей, филиала, дат, тарифов,
суммы строк, fingerprint подтверждения и транзакционного повторного выполнения.
Новые начисления, восстановления и объединения в production не выполнялись.

## Влияние и публикация

Проданное окружение и FFULHAB не менялись. POST/GET совместимы; UI-фильтр относится
к явному выбору клиента. Исключение классификации ограничено конкретным клиентом
и доказанными документами нашей ВМС; для остальных клиентов правила прежние.
Если переносить эти общие модули в проданную ВМС, транспорт и UI также изменятся —
такой перенос отдельно не разрешён.

Публиковать API перед вебом: старый веб совместим с новым API благодаря GET,
а новый веб требует POST. Нужен отдельный согласованный PR и релиз с актуальной
базой production; не заменять весь сервер устаревшим локальным checkout.
