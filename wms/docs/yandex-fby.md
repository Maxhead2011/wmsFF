## Рабочий сценарий

В разделе ФБО четыре одинаковые плитки: WB, Ozon, Lamoda, Яндекс. Сетка: две колонки, четыре на широком экране, одна на телефоне.

В Яндексе пользователь выбирает своего клиента, подключённый кабинет и доступный филиал. Можно загрузить существующую поставку по номеру/ссылке либо создать внутреннюю сборку из Excel (колонки `ШК`, `Количество`) или вручную. Перед созданием обязательны проверка состава, сопоставлений и доступных остатков. Offer ID Яндекса не считается штрихкодом: пользователь явно задаёт складской ШК для каждой позиции импорта. Неоднозначные и чужие товары не принимаются.

Сборка записывается вместе с принадлежностью Яндексу и событием создания. Повторный импорт возвращает существующую сборку. Ручную сборку можно связать с поставкой при полном совпадении состава; количество не заменяется. Привязка и импорт используют общий транзакционный замок для внешней поставки и уникальное ограничение БД. Повторная сверка только показывает различия — отбор и упаковка не переписываются.

Отбор и упаковка используют общий механизм WMS. В собственной версии ТСД предусмотрена отдельная очередь FBY; старые очереди WB/Ozon исключают такие заявки. Выгрузки WB для FBY запрещены. После проверки упаковки предусмотрена отметка сдачи; отмена доступна для новой заявки с подтверждением.

## Границы

- API Яндекса используется только для чтения. Создание внешней поставки, отправка грузомест и получение этикеток не реализованы этим этапом.
- Поддерживаются отдельные SUPPLY поставки и дочерние поставки виртуального распределительного центра. Родительскую объединённую поставку нужно разделить по дочерним.
- Импорт: до 1000 позиций. Список сборок: последние 200 активных или завершённых. Чтение API ограничено страницами и таймаутом каждого запроса; при неполном ответе создание запрещено.
- Кабинет должен содержать ID кампании и Api-Key с доступом к поставкам FBY. Реальный импорт на клиентском кабинете и физическое сканирование не проверены: браузерные проверки используют изолированные ответы API.
