# Яндекс Маркет FBY

Состояние на 28.10.2026: реализация в `feature/yandex-fby-workspace`, **не опубликована**. Целевая ветка PR: `feature/wb-print-check`. Проданная WMS не включается в выпуск.

## Рабочий сценарий

В разделе ФБО четыре одинаковые плитки: WB, Ozon, Lamoda, Яндекс. Сетка: две колонки, четыре на широком экране, одна на телефоне.

В Яндексе пользователь выбирает своего клиента, подключённый кабинет и доступный филиал. Можно загрузить существующую поставку по номеру/ссылке либо создать внутреннюю сборку из Excel (колонки `ШК`, `Количество`) или вручную. Перед созданием обязательны проверка состава, сопоставлений и доступных остатков. Offer ID Яндекса не считается штрихкодом: пользователь явно задаёт складской ШК для каждой позиции импорта. Неоднозначные и чужие товары не принимаются.

Сборка записывается вместе с принадлежностью Яндексу и событием создания. Повторный импорт возвращает существующую сборку. Ручную сборку можно связать с поставкой при полном совпадении состава; количество не заменяется. Привязка и импорт используют общий транзакционный замок для внешней поставки и уникальное ограничение БД. Повторная сверка только показывает различия — отбор и упаковка не переписываются.

Отбор и упаковка используют общий механизм WMS. В собственной версии ТСД предусмотрена отдельная очередь FBY; старые очереди WB/Ozon исключают такие заявки. Выгрузки WB для FBY запрещены. После проверки упаковки предусмотрена отметка сдачи; отмена доступна для новой заявки с подтверждением.

## Границы

- API Яндекса используется только для чтения. Создание внешней поставки, отправка грузомест и получение этикеток не реализованы этим этапом.
- Поддерживаются отдельные SUPPLY поставки и дочерние поставки виртуального распределительного центра. Родительскую объединённую поставку нужно разделить по дочерним.
- Импорт: до 1000 позиций. Список сборок: последние 200 активных или завершённых. Чтение API ограничено страницами и таймаутом каждого запроса; при неполном ответе создание запрещено.
- Кабинет должен содержать ID кампании и Api-Key с доступом к поставкам FBY. Реальный импорт на клиентском кабинете и физическое сканирование не проверены: браузерные проверки используют изолированные ответы API.

- `apps/api/src/modules/yandex-fby/`: клиент API `supply/items`, проверки входа, контроллер, `preview/create/bind/refresh`, `fbyQueueScope`.
- `apps/api/prisma/schema.prisma`, миграция `20261028130000_yandex_fby`: дополнительная таблица `YandexFbyShipment`, уникальные связи, без изменения остатков.
- `client-requests.service.ts`: связь в списке, защита состава. `client-request-marketplace-files.service.ts`: запрет файлов WB.
- `tsd-assembly.service.ts`, `fbo-two-stage.service.ts`: отдельная очередь и тип площадки. `app.module.ts`, реестр внутреннего API: регистрация модуля/маршрутов.
- `apps/web/src/components/yandex-fby/`, `FboWorkspace.tsx`, `fbo.css`, `fboRequestScope.ts`, `lib/api.ts`: две формы, привязка, сверка, плитки и исключение из WB.
- Android `MainActivity.java`, `FboTwoStageScreen.java`: очередь и завершение без файлов WB. Версия logoff 235; prod APK пока не заменён.

Android: полный `testLogoffDebugUnitTest` (266 тестов) и сборка debug APK 235. Миграция проверена в отдельном пустом PostgreSQL без портов/сети: уникальности, FK, ручные заявки, каскад. Production-данные не менялись.

Итог: API 3807 passed / 150 skipped; web 514 passed / 2 skipped; Android 266 passed. Два специальных KIZ DB integration файла исключены (для них нужен отдельный стенд). Пропуски не считаются успешными проверками. В web build остаются прежние предупреждения размера чанков и отсутствующего локального шрифта Jura-Medium.ttf.

Браузерная проверка: запустить Vite на 5189 с `VITE_YANDEX_FBY_ENABLED=true`, `VITE_LAMODA_ENABLED=true`; затем `node wms/scripts/tests/yandex-fby-browser.cjs`. Скрипт временно копирует тестовые точки входа из `scripts/tests/fixtures/yandex-fby`, удаляет их при завершении. Зависимость Playwright используется из локального Codex runtime.

Новые флаги: API `WMS_YANDEX_FBY_ENABLED`, web `VITE_YANDEX_FBY_ENABLED`; по умолчанию выключены. Android-пункт только в logoff flavor. Включать только совместно после миграции в нашей WMS. При выключенном API-флаге старые очереди не обращаются к новой связи.

Перед публикацией заново проверить live image и `current-production.md`. `sourceParityVerified=false`: полную локальную сборку поверх production не ставить. Нужен проверенный адресный overlay, миграция, совместимый Prisma Client, проверки собранного API/web/APK и baseline check-candidate. После появления FBY-заявок нельзя просто выключить фильтрующий API-флаг: они снова станут видны старым очередям. Для отката сначала закрыть доступ к новым операциям FBY, сохранить фильтрацию и таблицу связей; не удалять бизнес-данные.
