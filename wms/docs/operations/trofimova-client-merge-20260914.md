Новые отличия сумм, активный физический отбор, неизвестные зависимости или повторно выставленные строки счетов запрещают применение.

## Проверенный состав операции

- Сохраняются 5 заявок (242, 336, 461, 950, 951) с исходными номерами, статусами и филиалами. 951 относится к Казани, не переименовывать её филиал.
- Переносятся 3 счета общей суммой 5519.67 руб., договор, уведомления и 2 исходных движения товара. Количество и даты движений не меняются.
- Три пары SKU объединяются по проверенным артикулам/ШК/размерам/цветам; целевые карточки остаются неизменными.
- 69 дублирующих черновиков начислений удаляются; 4 уникальных переносятся. У трёх строк счетов меняется только ссылка на начисление, не сумма счета.
- 144 старые задачи — только WAITING_STOCK/RELEASED без начала сборки, КИЗов, резервных коробов и отгрузки. Сохраняются действующие задачи основного кабинета.
- 4 повторные связи заказов удаляются только из отменённых заявок; 9 уникальных переносятся.
- На снимке 143 дубли мониторинга; все 716 записей их истории сохраняются под целевыми событиями. Исторические sourceIds не переписываются.
- Доступ трёх сотрудников переносится с исходными правами. Существующие права основного клиента и его сотрудников не меняются.
- Старая карточка, её повторные SKU/ШК и повторное подключение WB удаляются после проверки ссылок. Список удалённых ID записывается в AuditLog, полные исходные данные остаются в резервной копии.

## Порядок production-применения (после согласования PR)

1. Сверить хост/контейнер/релиз именно `wms.logoff.pro`, проверить актуальный код и новый preview.
2. Сделать свежий проверенный pg_dump, если после снимка продолжалась работа. Зафиксировать SHA256.
3. Отключить **только** старое подключение WB `df5a51cf-e69b-4f0a-bd51-be0b72ac0ced` штатным способом. Основное `29bd3d2a-f6c8-4066-aa71-fc3b9335c7d5` не отключать.
4. Подтвердить завершение ранее запущенных фоновых запросов старого подключения. Не считать установленный isActive=false доказательством отсутствия уже загруженных запросов. Если их завершение нельзя подтвердить, не запускать merge: согласовать короткое окно обслуживания нашего API. Проданный API не останавливать.
5. Передать скрипту проверенный ADMIN userId исполнителя, SHA256 и подтверждение завершения фоновых работ. Не подставлять случайного администратора. Для репетиции использована административная запись «Костя».
6. Запуск по умолчанию — только read-only preview. Для реального выполнения необходимы одновременно `--apply`, `WMS_OUR_VM_CLIENT_MERGE=CL-000009`, `WMS_MERGE_ACTOR_ID`, `WMS_MERGE_BACKUP_SHA256`, `WMS_MERGE_OLD_CONNECTION_DRAINED=df5a51cf-e69b-4f0a-bd51-be0b72ac0ced` и неактивное старое подключение в БД.
7. Скрипт повторяет все проверки и выполняет одну SERIALIZABLE-транзакцию. Конкурирующее изменение или блокировка более 2 секунд останавливает операцию. Короткие блокировки затронутых таблиц запрещают запись, но не чтение; на репетиции весь запуск занял менее 6 секунд.
8. Проверить одну карточку CL-000009, доступные документы/заявки, отсутствие исходных ссылок, неизменность остатков и AuditLog `MERGE_TROFIMOVA_20260914`. Проверить повторно после цикла фонового обновления; клиенту обновить страницу/выбор кабинета.

## Восстановление

До commit ошибка откатывает всю транзакцию автоматически. Повторное применение после commit ничего не делает.
Если ошибка найдена после commit, не восстанавливать весь production-бэкап поверх новых заказов других клиентов. Восстановить бэкап в изолированную БД, сопоставить изменённые строки по AuditLog и подготовить адресный обратный перенос с учётом новых операций; согласовать его отдельно.
