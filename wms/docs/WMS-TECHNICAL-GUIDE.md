# WMS LOGOFF — техническое руководство

## 1. Архитектура

Система состоит из:

- NestJS API (`apps/api`);
- React/Vite web (`apps/web`);
- Android TSD (`apps/android-tsd`);
- Android WMS-приложения, если оно присутствует в сборке;
- PostgreSQL основной базы;
- отдельной PostgreSQL базы аналитики;
- Redis;
- Nginx;
- Docker Compose production-контура.

Основная цепочка запроса:

`Nginx → API controller → AuthGuard → permission/client scope → service → Prisma transaction → PostgreSQL → AuditLog`.

## 2. Модель доступа

JWT содержит только идентификатор пользователя и данные устройства. На каждом запросе AuthGuard заново загружает статус, роли, permissions и client scopes. Это позволяет блокировать пользователя без ожидания истечения токена.

Особые поля:

- `administrationEnabled` вычисляется по `administration.ownerUserIds`;
- `workspaceVisibility` загружается из `ui.workspaceVisibility`;
- `hiddenClientIds` не даёт внутреннему рабочему интерфейсу смешивать demo и production.

Проверки выполняются в порядке:

1. валидный Bearer token;
2. активный пользователь;
3. permissions;
4. owner allowlist для администрации;
5. client scope;
6. предметные бизнес-ограничения.

## 3. Складской инвариант

Остаток определяется ключом:

`clientId + skuId + boxId/palletId + stockStatus`.

Любое изменение физического количества обязано:

- выполняться в транзакции;
- создать `StockMovement`;
- использовать idempotency key;
- не делать количество отрицательным;
- корректно обработать ProductMark/КИЗ;
- сохранить источник документа и автора.

Короб уникален в установленной модели данных. Нельзя создать второй физический короб с тем же номером. Пустой короб архивируется, но его история остаётся.

## 4. Приёмка

`WarehouseService` ведёт online receipt поверх коробов, остатков, движений и операций ТСД. Дата партии извлекается из `receiptPrefix + DDMM[_]`. Настраиваемый `receiptPrefix` используется и при фильтрации файлов приёмки.

Валидация скана различает:

- короб — начинается с разрешённого префикса;
- товарный ШК — не длиннее разрешённого формата и не является коробом;
- КИЗ — длинная маркировка, не являющаяся коробом.

## 5. Заявка и резерв

Заявка содержит строки требуемых SKU. Резерв должен привязываться к единицам, а не блокировать короб. Для маркированного товара предпочтителен конкретный ProductMark, но при конфликте сборка должна уметь выбрать следующую свободную метку или выполнить контролируемую фактическую привязку.

Статус «Сдано» допустим только после:

- проверки количества;
- разрешения всех незакрытых позиций;
- фактического источника списания или явного «Без короба»;
- финансовой автоматизации, если она требуется.

## 6. FBS

Основные сущности:

- marketplace connection;
- WB order;
- shipment/group;
- WMS client request;
- assembly task;
- package/cargo place;
- picked unit и ProductMark;
- WB sticker/QR.

Синхронизация должна быть идемпотентной по WB order ID. Изменение состава группы отражается в WMS-заявке. Отмена не должна оставлять активный резерв. Перенос несобранного заказа создаёт или обновляет новую группу, сохраняя историю исходной.

Перед передачей WB выполняется reconciliation локальной заявки с текущим API-состоянием WB.

## 7. Биллинг

Начисление создаётся из факта операции и тарифа, действующего для клиента. Приоритет:

1. фиксированный FBS turnkey;
2. индивидуальная услуга клиента;
3. общий каталог/калькулятор;
4. ручное начисление с причиной.

Повторная обработка одного события не должна создавать дубль. Для этого используется source + sourceId/idempotency.

## 8. Системные настройки

`SystemSetting` хранит JSON-значения. Доступ должен идти через `SystemSettingsService`, а предметная нормализация — через специализированный сервис, например `BoxCodePolicyService`.

Новая настройка обязана иметь:

- уникальный стабильный key;
- значение по умолчанию;
- тип и нормализатор;
- пределы;
- risk level;
- audit before/after;
- описание в админке;
- тест.

## 9. Встроенный ИИ

Рекомендуемая архитектура:

`prompt → policy filter → structured plan → preview → owner approval → allowlisted tool → validation → audit`.

Инструмент получает узкую JSON-схему. Например, изменение префикса принимает только строку префикса и не имеет доступа к shell. Ответ модели не является доверенным: сервер проверяет каждый аргумент повторно.

Для программных изменений ИИ создаёт change request, а не правит production напрямую. Полный безопасный контур требует изолированного репозитория, тестовой среды, diff review, резервной копии, сборки, health-check и автоматического rollback.

## 10. Локальная разработка

Из корня проекта:

```powershell
pnpm install
pnpm prisma:generate
pnpm --filter @logoff/wms-api lint
pnpm --filter @logoff/wms-web lint
pnpm --filter @logoff/wms-api test
pnpm build
```

Перед коммитом:

```powershell
git diff --check
git status --short
```

Не включайте в репозиторий `.env`, дампы БД, APK-ключи, marketplace token и OpenAI API key.

## 11. Production deployment

Штатный порядок:

1. проверить свободное место и состояние контейнеров;
2. сделать резервную точку;
3. передать только проверенные исходники;
4. при изменении Prisma создать и проверить migration;
5. собрать API и web;
6. перезапустить только затронутые сервисы;
7. дождаться health status;
8. проверить `/api/v1/health`, вход, обзор, критический сценарий;
9. проверить логи;
10. сохранить идентификатор версии и план rollback.

Не используйте `git reset --hard` на сервере с несохранёнными изменениями.

## 12. Резервное копирование

Минимальная резервная точка:

- `pg_dump -Fc` основной базы;
- `pg_dump -Fc` аналитики;
- `pg_dumpall --globals-only`;
- Redis dump;
- исходники и конфигурация;
- Nginx/SSL-конфигурация без публикации приватных ключей;
- SHA256SUMS.

Проверка:

```bash
sha256sum -c SHA256SUMS
pg_restore --list main.dump >/dev/null
pg_restore --list analytics.dump >/dev/null
```

Rollback приложения и восстановление данных — разные операции. Базу восстанавливают только если новая версия действительно изменила данные несовместимым образом.

## 13. Наблюдаемость

Следить за:

- HTTP 5xx и временем ответа;
- event loop/API memory;
- PostgreSQL connections, locks и slow queries;
- Redis memory;
- частотой фоновых синхронизаций;
- повторными запросами UI;
- размером таблиц движений, операций ТСД и аудита;
- свободным диском;
- сроком действия токенов WB.

Индекс нужен под реальный фильтр. Перед добавлением индекса подтвердите slow query через `EXPLAIN (ANALYZE, BUFFERS)` на безопасной выборке.

## 14. Тестирование

Для критических сценариев нужны:

- unit-тест нормализатора;
- service-тест транзакции;
- API permission test;
- idempotency test;
- negative stock test;
- smoke test web;
- тест повторного скана на ТСД;
- тест reconciliation FBS;
- тест начисления без дубля.

## 15. Секреты

Пароли VPS, API marketplace, JWT signing secret, Firebase credentials и OpenAI key должны храниться только в secret/environment production. В логах показываются masked identifiers и сроки действия, но не значение ключа.
