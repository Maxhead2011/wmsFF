# Следующее изменение от текущей базы

1. Читать [паспорт](current-production.md), [карту](project-map.md) и [индекс тестов](test-index.md).
   Проверить чистоту рабочей ветки и фактическую актуальную интеграционную ветку.
   Новая `fix/...` или `feature/...`, без прямого push в базовую/защищённую ветку.
2. Считать свежие image ID API/web и метаданные APK. Сопоставить с манифестом.
   Если сервер новее — сначала сверить новый выпуск. Не накладывать старый модуль поверх нового.
3. Перечислить меняемые файлы/функции и связи с проданной WMS. Доработка одной
   функции не разрешает замену общего модуля старой сборкой.
4. Выполнить `python scripts/release_baseline.py verify` из `wms/`.
   Восстановить runtime в **новый** рабочий каталог:

   ```text
   python scripts/release_baseline.py materialize --target <work/new-candidate>
   ```

5. Вносить только проверенный delta в нужные файлы кандидата. Исходники менять
   и тестировать в Git. Пока `sourceParityVerified=false`, полный локальный dist
   не заменяет кандидат. Не копировать весь сервис из старого рабочего каталога.
6. Проверить точный состав изменения:

   ```text
   python scripts/release_baseline.py check-candidate --target <work/new-candidate> --base-image <fresh-live-api-image> --allow modules/tsd/tsd-device.controller.js
   ```

   `--allow` повторяется для каждого намеренно изменённого/добавленного файла.
   Удаления запрещены этой проверкой. Не расширять allow-list ради устранения
   ошибки: сначала выяснить, почему изменился посторонний файл. Хеши проверяют
   **состав**, поведение изменённых файлов проверяют тесты.
7. Запустить подходящие и общие тесты; для FBS обязательно проверить реальный
   candidate runtime. Оформить PR в согласованную ветку нашей WMS. Пропуски тестов,
   влияние на общие модули и источник runtime указать в описании.
8. Публикация только в согласованный контур. Под блокировкой выпуска повторно
   проверить текущий image ID; сохранить прежний образ для отката. Health-check,
   хеши опубликованных файлов и проверки сценария обязательны. Не менять БД,
   секретную конфигурацию или sold WMS в рамках публикации документации/снимка.
9. После успешного выпуска обновить паспорт, манифест/снимок и затронутую карту
   или индекс. Сохранить предыдущий снимок как историю. Обновить указатель актуальной базы.

Скрипт не подключается к серверу и не публикует код. Поэтому это обязательная
проверка процесса, а не утверждение, что все исторические deploy-скрипты технически
заблокированы. Не использовать обходной старый deploy вместо этой последовательности.

## Сведение исходников с runtime

Начинать с `divergence.json`. По одному модулю восстановить исходники из проверенных
Git-изменений и контейнерного source-reference, скомпилировать, сравнить с runtime,
воспроизвести необходимые сценарии. Сохранить документированный допустимый diff,
если отличие вызвано инструментарием компиляции. Не переносить серверные `.bak`,
generated-клиенты и секреты. Только после полной проверенной воспроизводимости
менять `sourceParityVerified` на `true` и разрешать полную сборку этого контура.
