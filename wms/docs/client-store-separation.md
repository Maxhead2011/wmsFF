# Магазины одного плательщика и общий физический товар

Статус: рабочая ветка `fix/client-store-separation`, не опубликовано. Флаг
`WMS_CLIENT_STORES_ENABLED` по умолчанию выключен. Никакие подключения,
остатки, КИЗы, заявки или настройки production этой работой не изменены.

## Подтверждённое правило

Один клиент WMS остаётся плательщиком. Монларти и Брайбо — разные магазины,
каждый со своими подключениями WB и Ozon. Бренд не является идентификатором
магазина: каталог WB Монларти содержит также LOUI VEARNER и Karaina.

30.10.2026 пользователь подтвердил: синие и чёрные «КостюмБомбер» — общий
физический товар для обоих магазинов. Разделять их SKU/КИЗы/балансы нельзя.
Резервы учитываются по физическому SKU один раз, совместно для всех
подключений и ФБО/ФБС. Переключение магазина не меняет количество товара.

Предварительная сверка файлов и WB выявила 10 SKU с ШК обоих магазинов.
На пяти SKU синего костюма суммарный баланс 108 единиц в восьми коробах.
Это не утверждение о свободном остатке: SKU участвуют в заявках 2528–2533.
Для активации требуется свежая сверка существующим расчётом резервов.

## Реализованная часть

- `client-stores.policy.ts`: проверка уникальных подключений, классификация
  единого SKU как STORE/SHARED/UNASSIGNED/REVIEW, без изменения склада.
- `client-stores.service.ts`: справочник `client.stores.v1:<clientId>` в
  существующих SystemSetting, проверка доступа клиента и demo, запись только
  ADMIN/OWNER, аудит, запрет незаметного переноса подключения между магазинами.
- `GET/PUT clients/:clientId/stores`: только метаданные. Ответ не содержит ключей API.
- Ответ списка FBS дополняется магазинами только после существующего ограничения
  по клиенту/филиалу. Невидимые подключения не раскрываются.
- В FBS появился фильтр магазинов и подпись магазина в строке. Неопределённые
  подключения доступны через «Без магазина» и не присваиваются по имени.

## Продолжение: приёмка и общий SKU

- `GET/PUT clients/:clientId/stores/skus/:skuId`: явные разрешения одного SKU
  для одного или нескольких магазинов. Проверяются клиент, роль ADMIN/OWNER,
  исходная версия связей; удаление разрешения блокируется до сверки резервов.
- `assertStoreReceipt` вызывается внутри транзакции `receiveIntoBox` до записи
  остатков и КИЗов. Неизвестный магазин/товар не создаёт приход. Документ
  приёмки закрепляется за магазином под той же блокировкой, что и настройки.
- `RECEIPT_STORE_RECORDED` сохраняет магазин на конкретном движении склада.
  Это аналитический контекст, а не отдельный остаток магазина.
- Парсер ТСД, синхронизация и ручной разбор сохраняют `storeId` из исходного
  скана. Старые сканы без него при включённом справочнике требуют разбора.
- LOGOFF показывает выбор магазина перед приёмкой, восстанавливает выбор
  вместе с документом и копирует его в стандартный скан и пакет закрытия короба.
  Другие варианты приложения сохраняют прежний экран.
- Сервер отдаёт ТСД только id/название магазина для уже доступного клиента,
  без реквизитов и секретов подключений. Новые маршруты внесены в реестр API.

Строгая приёмка остаётся выключенной до обновления ТСД, заполнения
проверенных разрешений SKU и разбора старых очередей. Настройки и метаданные
магазинов публикуются отдельно под WMS_CLIENT_STORES_ENABLED.

3. Проверить все способы ручной и автоматической сборки/объединения по подключению.
   Метаданные в заявках, плане ФБО и на ТСД добавлены; старые смешанные заявки
   требуют отдельного разбора.
4. Связать общие товары с существующим multishop stock механизмом, не добавляя
   второй расчёт остатков и не включая публикацию без сверки маршрутов.
5. Проверить детализацию на реальных начислениях: магазин добавлен к начислениям
   со связанной заявкой. Общескладские услуги без заявки остаются у плательщика.
6. Проверить неоднозначные/ненайденные позиции старого каталога. Применение
   исторических привязок — отдельная операция по предварительному отчёту.
7. Полные тесты, интеграционные проверки БД/браузера/ТСД, актуальная production
   база, PR и отдельная публикация. Проданная WMS не входит в выпуск.

Нельзя включать строгую приёмку и считать разделение завершённым только по наличию фильтра.

## Настройки и отображение магазина

`ClientStoresSettings` включается `VITE_CLIENT_STORES_ENABLED=true` только для
ADMIN/OWNER. Связи кабинетов нельзя незаметно перепривязать, разрешения общего SKU
добавляются с проверкой исходного значения. Поиск ограничен клиентом.

`requestStoreContexts` читает только уже разрешённые пары requestId/clientId.
Источник — FbsOrderRequestLink или OzonFboShipment.integration.connectionId.
Магазин не угадывается по бренду, имени заявки или SKU. ASSIGNED, MIXED, UNASSIGNED
отображаются в заявках и начислениях; LOGOFF показывает магазин при отборе и упаковке.

Флаги разделены: `WMS_CLIENT_STORES_ENABLED` разрешает настройку и метаданные;
`WMS_CLIENT_STORE_RECEIPTS_ENABLED` дополнительно включает обязательный магазин
при приходе и выбор на ТСД. Второй флаг нельзя включать до заполнения разрешений,
обновления устройств и проверки веб-приёмки. Производственные данные не изменены.

Повторная проверка настроек и отображения: API 4126 passed / 156 skipped
(отдельный PostgreSQL-набор исключён по причине выше), Web 570 passed / 2 skipped,
полные Android-наборы трёх вариантов прошли. TypeScript API/Web и diff check прошли.
