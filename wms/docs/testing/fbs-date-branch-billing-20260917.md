# FBS: разделение групп без поставки по филиалам

## Подтверждённый случай

ИП Бушкова И.М., клиент `00-00000039`. При открытом Ozon ошибка приходила из общего расчёта клиента, включающего WB.
Свежая проверка 17.09.2026 в 20:46 МСК выявила группу WB `date:2026-08-23`:

- Заявка 369, Казань: 5561861479, 5561861482, 5561861484.
- Заявка 355, Москва: 5557173928.
- У всех четырёх нет номера поставки. Совпадение даты не означает общую поставку.

## Изменение

Только API, без миграции БД, изменения тарифов, APK или веба.
`WMS_FBS_DATE_BRANCH_BILLING_ENABLED=true` вместе с существующим
`WMS_WB_ORDER_STOCK_LIFECYCLE_ENABLED=true` включает раздельные ключи датированных групп:
`<старый ключ>:warehouse:<филиал>`.

Филиал берётся из заявки, затем из резерва, как в прежней проверке.
Реальные поставки с `supplyId` не разделяются: защита от смешения филиалов остаётся.
Ключ стабилен при повторном расчёте и при частичном обновлении списка.

Перед расчётом читается история старых FBS/первичных счетов и начислений этого клиента:

- Если филиал старого ключа доказан, этот филиал сохраняет старый ключ, остальные получают отдельные ключи.
- Учитываются и отменённые/объединённые документы: переименование не должно обходить защиту истории.
- Старое начисление без доказуемого филиала или с конфликтующими филиалами останавливает запись с отдельным сообщением; денежные данные не угадываются.
- Уже существующие ключи филиалов и повторных попыток не принимаются за старые общие ключи.
- Существующая защита жизненного цикла сохраняет финансовые снимки и учитывает ранее начисленные услуги.

По умолчанию флаг выключен; проданная WMS сохраняет прежний путь без дополнительных запросов.
Включать только в нашей WMS после PR и отдельной публикации. Не переносить весь устаревший service-файл поверх новых production-изменений.

Первые два теста воспроизвели исходную ошибку до исправления.

## Ограничения публикации и отката

Репетиция на изолированной копии свежего production-дампа: исходная ошибка воспроизведена, неуспешная транзакция ничего не изменила. С исправлением все 243 прежних счёта (включая строки и оплаты) и 912 начислений сохранены без изменений. Разблокированный расчёт создал 222 новых черновых счёта/начисления, суммарно 10 170 ₽; повторный запуск не изменил снимок. Этот финансовый эффект отдельно согласован Константином: «Включить также расчёт Бушковой».

Исторические заказы без текущей заявки сохраняют старый ключ только при доказанной привязке конкретного orderId к старому FBS-начислению. Наличие одного лишь общего ключа недостаточно. Данный случай добавлен в 18-й тест.

Итоговый общий локальный прогон с исправлением авторов: 2682 API-теста прошли, 63 пропущены; 233 web-теста прошли. Typecheck обоих приложений и API build прошли.

До включения: свежая резервная копия, сверка live-кода и сравнение конкретных счетов до/после на копии БД. Не отменять/не переносить реальные счета автоматически.
После включения проверить общий список WB/Ozon клиента, создание только недостающих раздельных черновиков и повтор запроса без дублей.
При откате флага созданные документы не удалять и не сливать: старый код снова может выдать исходную блокировку для смешанной даты. Приостановить автоматический перерасчёт и проверить документы перед любым исправлением данных.
