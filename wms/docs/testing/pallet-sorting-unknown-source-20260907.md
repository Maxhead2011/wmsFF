# Неизвестный короб и новый КИЗ при административной сортировке

Дата: 07.09.2026. Ветка: `fix/sorting-unknown-source-recovery-20260907`.
Результат: исправление локальное; production, общий канал APK и физические ТСД не обновлялись.
Предлагаемая база PR нашей WMS: `fix/fbs-box-scan-route-consistency` (та же база, что у PR65).

## Сценарий и границы

Запрос Константина: неизвестный исходный короб не должен заставлять прерывать сортировку;
новая физически отсканированная пара ШК–КИЗ должна учитываться в целевом коробе, исходный короб — отмечаться проблемным.

- Только существующий раздел «Сортировка и перемещение», ADMIN и `WMS_PALLET_SORTING_ENABLED=true`.
- На старте паллет-сорта неподтверждённые связи с отсутствующим Box сохраняются в `problemSources`.
- Сканирование неизвестного короба отмечает проблему, но не создаёт ни Box, ни товар.
- Также поддержан исходный короб, отсканированный уже во время формирования целевых коробов.
- Если есть однозначный доступный источник в исходном составе, используется прежний парный MOVE без увеличения общего количества.
- Если источника нет, используется ровно один отсканированный проблемный короб. При нескольких требуется выбрать/сканировать нужный исходный короб в этом же экране.
- Найденная единица: отдельный `INVENTORY_ADJUSTMENT +1` и ProductMark в целевом коробе; не фиктивный расход из несуществующего короба.
- В счётчиках и итоговом окне найденные единицы отделены от обычных перемещений.
- Короб другого клиента/филиала, существующий короб вне состава и повторно зарегистрированный КИЗ не становятся «неизвестными» автоматически.
- Проверки истории: ProductMark, FbsTsdAssembly, ShippedKizHistory, FbsWebKizStickerPrint, FbsAssemblyAttemptHistory, FbsPrintJob, KizCirculationItem. Проверка глобальная, с вариантами записи разделителей/префикса, литеральными `%`, `_` и сохранением регистра серии.
- Клиент/SKU не создаются автоматически. SKU должен однозначно находиться по ШК у клиента сортировки.
- Подтверждение списания недостачи, блокировка полной инвентаризации и незавершённого пересчёта сохранены.
- Неизвестный короб остаётся в отчёте проблемным; вымышленная архивная Box-запись не создаётся.
- Старые JSON-сессии без новых полей совместимы; миграция базы не нужна.

### Настоящая PostgreSQL

Изолированная БД `sorting_recovery_test` в тестовом контейнере `sorting-pr63-postgres-20260907` на внутренней Docker-сети без доступа к WB. Скопирована только схема, все данные созданы тестом. Доступ к production использовался только для чтения схемы, live-таблицы не менялись.

Тест запускался на изолированном API-контейнере с двумя собранными JS-модулями этой ветки, смонтированными read-only. Основной API-контейнер не перезапускался.

Результат:

```json
{"result":"PASS","recovered":3,"ledger":3,"rollback":"PASS","concurrentRetry":"PASS","alternativeKizAndLiteralLike":"PASS","completion":"PASS"}
```

- Ошибка после записи движения/КИЗ при финальном аудите откатила всю транзакцию, включая счётчики сессии.
- Одновременная доставка одной команды и её повтор привели ровно к одной новой единице.
- Отгруженный КИЗ с альтернативным префиксом, другим криптохвостом и `%_` в серии не был принят повторно.
- Завершение не архивировало целевой короб; в нём осталось ровно 3 единицы.
- Неизвестный исходный короб не был создан в Box; проблема сохранилась.

Первые два запуска тестового стенда не считаются PASS: исправлена проверка готовности временного PostgreSQL (TCP вместо сокета при инициализации), затем исправлен тестовый серийный номер длиной 14 вместо 13 символов. После этого полный сценарий прошёл. Тестовый контейнер остановлен.
