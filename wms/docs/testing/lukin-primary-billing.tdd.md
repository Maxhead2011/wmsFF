# Первичная обработка Лукиных — исключение двойного начисления

Дата: 2026-09-14. Ветка: `fix/lukin-primary-billing-composition`.
База локальной работы: `fix/fbs-transfer-missing-active-orders`, `d2baa5d4`.

## Подтверждённая причина и границы

Read-only диагностика production (транзакция `SET TRANSACTION READ ONLY`):
у CL-000001 в настройках одновременно выбран тариф WHITE = 10 и дополнительная
услуга ITEM_PROCESSING = 10.64 INCLUDED. Генератор складывает оба начисления.
Для 12 единиц появляется лишняя строка WHITE на 120 рублей.
С допуслугами 12 × 4.26 и перемаркировкой 8 единиц пример даёт 383.91 вместо 263.91.
Тариф перемаркировки и существующий расчёт его налога не меняются.

Согласованный состав: допуслуги 4.26 INCLUDED и первичная обработка 10.64 INCLUDED
на каждую обрабатываемую единицу; перемаркировка — только при наличии.
Прочие услуги исключены только из этой автоматической первичной обработки,
не из всего биллинга клиента. Фиксированный FBS, логистика и хранение не изменены.

## Публикация и существующие счета

По умолчанию правило ВЫКЛЮЧЕНО. На нашей ВМС при отдельной публикации включить
`WMS_LUKIN_PRIMARY_SERVICE_POLICY_ENABLED=true` в окружении API.
Область — только проверенные CL-000001 и CL-000010 (точные UUID в модуле).
Для проданной ВМС флаг не включать; без флага и для прочих клиентов поведение прежнее.
Shared-модули API/web затронуты, поэтому это предупреждение необходимо включить в PR.

У CL-000010 первичная обработка сейчас отключена: исправление не включает её автоматически.
Если её включают отдельно, должны быть настроены обе обязательные услуги.
При отсутствующей или дублирующейся конфигурации правило останавливает расчёт до записи,
чтобы не формировать частичный счёт без первичной обработки.

Production-настройки, начисления и счета этим изменением НЕ исправлены и НЕ опубликованы.
После публикации нужен контролируемый пересчёт неоплаченных собственных черновиков:
сначала список и суммы до/после, затем штатная транзакционная генерация и повторная сверка.
Выставленные, оплаченные и объединённые счета требуют отдельного согласованного разбора;
массово удалять их строки нельзя. Отключение флага не возвращает уже пересчитанные суммы.

PR для нашей ВМС — в согласованную release-ветку `fix/fbs-transfer-started-at`.
Не публиковать весь checkout автоматически: база содержит отдельное ещё не опубликованное
исправление переноса заказов `d2baa5d4`. Для независимого релиза выделить только текущий
коммит в release-based fix-ветку после сверки с production либо согласовать отдельный stacked PR.
