# Просмотр FBS без ожидания сверки и имя автора заявки

Статус: подготовлено локально, **не опубликовано**. Только наша WMSFF2207.
Ветка: `fix/fbs-read-latency-request-author-20260916`.
База: `465a1ce8`, действующая интеграционная ветка `fix/fbs-transfer-started-at`
после PR 159 и 160. Новая ветка создана от прежней рабочей и обновлена только
fast-forward, без разрешения конфликтов. Проданная WMS, APK, БД и миграции не менялись.

## Причина и границы исправления

При диагностике production открытие кабинетов последовательно ожидало `loadFbsOrders`.
Этот путь включает сверку исторических отгрузок, изменение резервов и начисления.
В логах обнаружены повторяющиеся ошибки сверки, таймауты финансовых транзакций
60 секунд, HTTP 500 и прерванные запросы кабинетов. Быстрый `/health` не доказывал
исправность FBS. У отдельных кабинетов отдельно от этого отозваны ключи WB.

Новый режим `GET .../fbs/orders?view=snapshot` предназначен только для просмотра:

- возвращает существующий снимок, даже если он устарел; показывает его время;
- при холодном старте возвращает только сохранённые активные заявки WMS с явным
  `sync.partial=true`, пустой датой обновления и неизвестными полными счётчиками;
- обновляет список в фоне, не создаёт/снимает резервы, не списывает товар и не
  пересчитывает счета; читает существующие маршруты и факты отгрузок;
- не перезаписывает оперативный кэш, используемый сборкой и переносами;
- объединяет повторные обновления клиента, ограничивает их двумя параллельными
  клиентами и 128 записями, повторяет ошибки не чаще чем через 30 секунд;
- возвращает безопасное описание ошибки, без ключей, внешних тел ответа и SQL;
- сохраняет клиентские и филиальные проверки на каждом чтении;
- браузер опрашивает готовность через 5 секунд, пока обновление выполняется.

Старые вызовы без `view=snapshot`, проверки перед операциями, фоновая бизнес-сверка,
финансовая блокировка и правила расчёта не изменены. Это исправление ожидания экрана,
а не изменение или отключение обработки проблемных исторических отгрузок.
Первичная загрузка полного списка по-прежнему зависит от доступности маркетплейса.
Известные суммы обработки берутся из оперативного кэша; неизвестные остаются `null`,
а не нулём. Отозванный API-ключ нужно отдельно заменить в настройках кабинета.

В списке заявок рядом с «Создана» показано существующее `createdBy.name`.
Если имя не сохранено, выводится «Автор: не указан»; текущий пользователь и email
не подставляются. Схема и API заявки уже содержали автора, новые запросы не нужны.

  ошибка ключа WB, сохранение строк при HTTP 503; без JS-ошибок и внешних запросов.

### Окружение тестов

Старый общий Prisma Client не содержал моделей последних PR. Для выбранной рабочей
копии создан отдельный `apps/api/node_modules/@prisma/client` и выполнен `prisma generate`.
Общие зависимости других checkout не изменены. Добавлены локально уже зафиксированные
в lockfile `bwip-js 4.11.4` и `zxing-wasm 3.1.4` с проверкой SHA-512.

Первый полный прогон выявил существующую ошибку инициализации пропускаемого теста
`kiz-duplicate.integration.spec.ts`: Prisma Client создаётся с `url: undefined`
даже внутри `describe.skipIf`. Сам файл не изменялся. Финальный прогон использовал
явно пустую строку `KIZ_DUPLICATE_TEST_DATABASE_URL=''` в окружении дочернего процесса:
тест штатно пропущен, ни к одной БД подключения не было. Все DB-интеграционные пропуски
перечислены отдельно, не считаются успешными проверками.

Логи и скриншоты: `C:/WMSFF2207/reports/fbs-read-latency-20260916/`.
