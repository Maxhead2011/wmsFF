## Реализованный сценарий

1. Только ADMIN с выбранным филиалом открывает сортировку по паллет-сорту или одному коробу.
2. Состав паллет-сорта фиксируется в сессии. Администратор сканирует присутствующие короба; повторный скан не добавляет товар.
3. Отсутствующие короба показываются вместе с остатками. Архивирование и списание требуют свежего снимка и отдельного подтверждения недостачи.
4. Администратор открывает новый пустой целевой короб и указывает его фактический паллет-сорт. Несуществующее расположение не придумывается.
5. ШК → КИЗ перемещает одну единицу: существующий парный MOVE −1/+1 и перенос привязки КИЗ в одной транзакции с состоянием сессии. Новая приёмка и отгрузка FBS не создаются.
6. «Закрыть короб» закрывает только текущий целевой короб. Можно открыть следующий.
7. «Завершить сортировку» показывает оставшиеся исходные остатки. Недостача списывается только после отдельного согласия; обычные исходные короба архивируются и отсоединяются от паллетов через существующий сервис. Постоянные боксы, определённые существующей включённой политикой, остаются пустыми, активными и на своих местах. Такое же различие действует для отсутствующих исходных коробов.
8. Доступные оставшиеся КИЗ получают BLOCKED и сохраняют ссылку на исторический исходный короб. Исторические PACKING/SHIPPING не меняются. Уже перемещённые КИЗ остаются в новых коробах.
9. Затронутые, ещё не отобранные задания FBS получают перестроение по текущему наличию в выбранном филиале. Физические сканы и выполненная сборка не сбрасываются. Заказ WB не отменяется, в WB ничего повторно не отправляется.

Сессия сохраняется на сервере после каждого действия. Версия сессии, уникальный номер команды, отпечаток запроса и уникальные ключи движений защищают повторы. После неизвестного сетевого результата UI предлагает повторить ту же команду. Список незавершённых сессий позволяет продолжить после перезапуска.

## Ограничения и обязательные шаги до включения

1. Совместить с актуальной релизной веткой через PR. Конфликты не разрешать автоматически; после согласованного совмещения повторить полный прогон.
2. На отдельной тестовой PostgreSQL проверить запуск Nest/DI, применение additive migration, реальный MOVE −1/+1, атомарный rollback после ошибки КИЗ, параллельные администратор/сборщик, одинаковый operationId и рестарт сервера.
3. Проверить FBS до/после перемещения: источник обновлён, уже собранное не сброшено, нет второй отгрузки, нет прибавления остатка. При конфликте сохранения маршрут остаётся на повторе.
4. Незавершённые перестроения хранятся в сессии и повторяются при действии/возобновлении в вебе или кнопкой в ТСД. Автономного фонового worker для этой очереди нет.
5. Положительные складские остатки RESERVED/PACKING и прочие не-AVAILABLE, полная инвентаризация, COUNTING/MISMATCH и активная не-FBS заявка не обходятся. Логические задания FBS перестраиваются, но это не разрешение стереть чужое физическое действие.
6. Для неизвестного КИЗ при нескольких возможных источниках требуется указать исходный короб на том же экране. Излишек сверх учтённого AVAILABLE автоматически не приходуется: нужна отдельная актуализация. Новый сервис не заменяет весь модуль инвентаризации.
7. Большой паллет требует нагрузочной проверки: операция архивирования целиком транзакционная с timeout 30 секунд, разбиение на пакеты не внедрено.
8. Нужен пилот на одном согласованном ТСД. Собран только debug APK после совмещения с базой 158: не заменять им подписанный production APK. Подписанный APK/версия/канал обновления в задаче не менялись.
9. Перед разрешённым production-внедрением сделать свежую проверяемую резервную копию БД и текущих артефактов. Сначала миграция/код с выключенными флагами, затем проверка и включение для нашей системы. Отключение флага останавливает новые действия, но не откатывает уже совершённые складские движения; обратные операции требуют отдельного разбора.

Публикация до этих проверок не рекомендуется. Реальные короба, КИЗ, заявки и учётные данные не включены в новые фикстуры.

### Исторический блокер: постоянные боксы (решение подтверждено и реализовано ниже)

Существующие тесты прошли, но дополнительная проверка выявила несовместимость правил, которую они не покрывали:

- В релизе при `WMS_PERMANENT_STORAGE_BOXES_ENABLED=true` функция `preserveEmptyStorageBox` сохраняет постоянные боксы по настроенным префиксам на месте даже при нуле.
- Новая `PalletSortingService.archiveSources` переводит каждый исходный короб в archived.
- Переиспользуемый `ArchivedEmptyBoxPalletDetachService` теперь отказывается отсоединять постоянный бокс. Получается archived, но связь с паллет-сортом остаётся.

Это воспроизведено отдельным локальным диагностическим сценарием на скомпилированных сервисах и mock БД, без подключения к базе: `boxStatus=archived`, `stillOnPallet=true`, `sessionSaysArchived=true`. Временный сценарий находится вне Git, использует только синтетический SBOX_QA. Это подтверждение дефекта совместимости, не зелёный тест корректности поведения.

Нельзя молча отключать правило постоянных боксов ради сортировки или менять согласованное архивирование всех обычных исходных коробов. Нужно подтвердить: постоянные боксы после сортировки должны оставаться активными на месте либо для этого административного сценария допускается их отдельное архивирование с отсоединением. После ответа добавить регрессионный тест на совместное выполнение реальных сервисов, сделать локальную правку в новом сценарии и повторить проверки.

- Для обычного размещённого короба проверяется результат отсоединения. Если сервис отказал, выбрасывается ошибка для отката всей вызывающей транзакции. Реальный PostgreSQL rollback здесь ещё не проверен.
- В аудите каждого короба записывается результат `PRESERVED_ON_PALLET` либо `ARCHIVED`.
