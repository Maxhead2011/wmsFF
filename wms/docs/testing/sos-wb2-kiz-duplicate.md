# SOS WB2: дубль КИЗ

Ветка: `feature/sos-wb2-kiz-duplicate`, база: `fix/fbs-transfer-started-at`.

## Поведение

В SOS WB2 после входа доступна кнопка «Дубль КИЗ». Экран работает независимо
от выбранного FBS-заказа. Выбираются клиент текущего филиала и доступная
печатная станция 58 × 40 мм. После сканирования полного КИЗ приложение показывает
карточку для подтверждения. Если точный КИЗ и GTIN не определяют единственный
товар, запрашивается ШК. Противоречащий точной привязке известного КИЗ товар
отклоняется. Для неизвестного КИЗ история других кодов с тем же GTIN — только
подсказка: отсканированный ШК задаёт товар на этикетке, даже если его нет среди
предположений по GTIN. Это не создаёт привязку маркировки к товару.

Сопоставление для подписи не регистрирует ProductMark, не изменяет остатки,
не резервирует заказы и не вызывает WB. Поиск использует только данные
выбранного доступного клиента. Для складского сотрудника без индивидуального
списка клиентов используется список его текущего филиала, как в существующем
SOS-процессе; не-складским ролям этот fallback не предоставляется.

Поддержан используемый на складе формат одежды: AI 01 (GTIN-14), AI 21
(13 символов), GS, AI 91 (4 символа), GS, AI 92. Проверяется структура и
контрольная цифра GTIN, но не криптографическая подлинность кода. Удаляются
только префикс сканера `]d2` и завершающие CR/LF. Пробелы не исправляются,
строки не склеиваются, регистр и пунктуация сохраняются. Обрезанный код или
неподдержанный формат требуют полного оригинала; из названия КИЗ не создаётся.

После печати сотрудник повторно сканирует физическую этикетку. `PRINTED`
означает успешную передачу в Windows-печать; `VERIFIED` - совпадение полного
повторного скана. PDF-импорт и выпуск нового КИЗ в этот режим не входят.

## Очередь и восстановление

Новые таблицы `KizDuplicatePrinter` и `KizDuplicateJob` изолированы от FBS.
Обновлённый агент регистрирует готовность, филиал и свой аккаунт отдельным
heartbeat. Старый агент не получает эти задания. В очереди хранится ровно
одна готовая PNG-этикетка; сортировочная наклейка не добавляется.

Идентификатор запроса сохраняется на устройстве до отправки и повторно
используется при обрыве связи. Изменённый запрос с тем же ID отклоняется.
Выдача агенту атомарна (`FOR UPDATE SKIP LOCKED`). Автоматической повторной
выдачи `CLAIMED` нет: при неизвестном результате нужно проверить принтер.
Повтор результата от агента не запускает повторную физическую печать.
История доступна владельцу заданий в текущем филиале; в AuditLog сохраняются
оператор, код, товар, станция, запрос, результат и подтверждение сканированием.

## Изоляция проданной ВМС

Все новые API-пути требуют `WMS_KIZ_DUPLICATE_ENABLED=true` и права `print:write`
(или `system:admin`). По умолчанию функция выключена. Существующие очереди,
статусы, шаблоны, FBS-методы и Android TSD не изменяются. Новая ветка не должна
публиковаться в проданную ВМС; при переносе общих файлов флаг оставлять выключенным.

```powershell
# apps/api
node node_modules/prisma/build/index.js generate

# Для интеграционных тестов - только отдельная локальная тестовая база:
$env:KIZ_DUPLICATE_TEST_DATABASE_URL='postgresql://codex_tests@127.0.0.1:55469/kiz_duplicate_tests?schema=public'
node node_modules/vitest/vitest.mjs run test/kiz-duplicate.integration.spec.ts
# apps/windows-print-agent
node --test agent.test.cjs kiz-duplicate.test.cjs
# apps/android-sos-wb
gradle testDebugUnitTest assembleDebug assembleRelease
```

Тесты декодируют итоговое изображение другим движком и проверяют все байты
и GS1-идентификатор `]d2`, включая буквальные `^FNC1`, запятые и точки с запятой.
PostgreSQL-тесты проверяют конкурентное создание/выдачу, аудит, повтор ответа,
проверку этикетки и отсутствие изменений ProductMark/StockMovement/FBS.

## Установка после согласования PR

1. Проверить актуальную рабочую ветку и runtime сервера. Применить только
   согласованные изменения и аддитивную миграцию. Не запускать массовый
   `db push` или непроверенную цепочку старых миграций на рабочей базе.
2. Включить флаг только нашей ВМС, проверить API под обычным оператором.
3. Установить обновлённый агент в каталог действующего агента, сохранив
   `config.json`. Аккаунт агента должен иметь текущий филиал и право печати.
4. Подписать release APK прежним ключом приложения `pro.logoff.wms.soswb.v2`.
   Debug APK и unsigned APK не подходят для обновления рабочего приложения.
5. Проверить один дубль на реальном ТСД/принтере: 58 × 40 мм, правильная подпись,
   ровно одна этикетка, повторный скан `VERIFIED`. Убедиться, что печать WB
   продолжает выдавать прежнюю пару этикеток.

Физический ТСД не был подключён к рабочему компьютеру при локальной проверке;
реальная печать и обновление установленной APK проверяются при внедрении.
