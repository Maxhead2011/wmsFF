# Старые остатки PACKING и клиентский доступный остаток

## Исправление механизма

`donePackingQuantity` учитывает время движений: корректировка другого документа,
сделанная до первого отбора новой заявки, не может списывать её будущий товар.
Сумма истории обязана совпадать с текущим остатком, а собственное сальдо заявки —
помещаться в нём. При неизвестных датах или более позднем неоднозначном списании
закрытие по-прежнему останавливается. Входные точки существующего закрытия и
фоновой сверки не меняются. Флаг `WMS_DONE_PACKING_RECONCILIATION_ENABLED`
сохраняется; проданная ВМС без него не затронута.

## Историческое исправление

`historical-packing.ts` работает по точной ячейке: клиент, филиал, SKU, короб,
паллет. Положительные остатки только сданных OUTBOUND/DELIVERY заявок допускаются
к очистке. Группы с положительными движениями после указанной границы исключаются.
Все нераспределённые отрицательные сальдо сначала поглощают старый допустимый
остаток; активный и сегодняшний товар не используется для финансирования списания.

Для заданий FBS проверяется принадлежность заявке. Если задание удалено, требуется
неизменяемая запись `WbOrderShipment` либо `ShippedKizHistory` с совпадающими
заявкой, клиентом, SKU и филиалом, достаточным количеством и датой до границы.
Сохранившееся задание, перенесённое в другую заявку, этой заменой не обходится.
Записи отгрузок и сами КИЗы не изменяются.

Каждая корректировка — `INVENTORY_ADJUSTMENT/PACKING` с ключом
`historical-packing:<fingerprint>:<requestId>`. Это не повторная отгрузка для
отгрузочных отчётов. AVAILABLE, SHIPPING, цены и начисления не изменяются.

Пример из каталога API:

```text
node dist/scripts/repair-historical-packing.js --before=2026-09-20T00:00:00+03:00 --plan=reviewed-plan.json
```

Предпросмотр выполняет только READ ONLY транзакции и создаёт новый файл плана
без перезаписи существующего. Для применения того же плана:

```text
WMS_HISTORICAL_PACKING_REPAIR_ENABLED=true
node dist/scripts/repair-historical-packing.js --before=2026-09-20T00:00:00+03:00 --plan=reviewed-plan.json --apply
```

Первая строка обозначает переменную окружения процесса, а не универсальную команду
оболочки. В рабочей ВМС её передавали только служебному процессу через Docker exec.
Флаг по умолчанию выключен; автоматического фонового запуска скрипта нет.

Применение блокирует заявки, затем задания, затем остаток; пересчитывает план
после блокировки и сравнивает fingerprint истории, владельцев и доказательств.
Новый скан, изменение статуса или остатка запрещает применение устаревшего плана.
Проверка и все движения конкретной ячейки находятся в одной транзакции.
Повторный предпросмотр после исправления возвращает нулевой план.

## Клиентская выдача

`WMS_CLIENT_PALLET_SORT_FREE_STOCK_ENABLED=true` усиливает серверную выдачу для
кабинета/Excel: свободное количество учитывается только у AVAILABLE с реальной
привязкой короба к палетсорту того же клиента и филиала. Из него один раз вычитаются
резервы. CLIENT получает только положительные свободные строки; его `quantity`
равно `freeQuantity`. Внутренним пользователям сохраняются физические количества,
а `freeQuantity` остаётся безопасным источником для клиентского экспорта.
Без нового флага поведение существующей установки сохраняется.

Это меняет клиентскую политику в том числе для режимов BOXES/без коробов при
включении нового флага: товар вне палетсорта не является клиентским доступным
остатком. Включать флаг только в нашей ВМС по согласованной политике.
