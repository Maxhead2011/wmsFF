# Возобновление частично завершённой автосборки

Автосборка могла создать WMS-заявку, затем получить конфликт записи резервов или ошибку WB. Следующий запуск исключал заказ по существующей связи с заявкой. Для этой ситуации добавлен отдельный восстановитель: перед выбором новых заказов `AutoAssemblyService.run` проверяет ошибки ранее созданных автоматических заявок.

## Границы и включение

- Нужны одновременно `WMS_AUTO_ASSEMBLY_ENABLED=true` и `WMS_AUTO_ASSEMBLY_RECOVERY_ENABLED=true`. Новый флаг по умолчанию выключен; проданная ВМС сохраняет прежнее поведение.
- Только WB, существующие заявки своего клиента/кабинета с записанной ошибкой автоматического запуска. Отменённые и завершённые заявки не возобновляются. Ручные заявки не подбираются.
- Проверяются текущие настройки выбранных складов. Если склад исключили из расписания, восстановление выдаёт отдельную ошибку вместо переноса.
- Источник текущего статуса — WB orders/status, источник состава — order-ids. Прогретый кэш истории не нужен.
- Автоматически обрабатывается одна поставка на заявку, до 100 новых заказов, без обязательного создания грузомест. Несколько поставок, физически начатый отбор новых заказов, неизвестный склад и грузоместа требуют отдельного решения. Ошибка остаётся видимой в PARTIAL.
- Поля маршрутизации `sellerWarehouseId/Name` должны присутствовать в рабочей схеме. Старые схемы без них останавливают восстановление; миграций этот PR не вводит.

## Защита от повторов

`SystemSetting` с ключом `fbs.autoAssembly.recovery.<connectionId>.<requestId>` хранит этап: CREATE_PENDING → SUPPLY_CREATED → ASSIGN_PENDING → VERIFY_PENDING → VERIFIED. Намерение создать поставку сохраняется до POST; полученный номер — до PATCH. Ошибка или тайм-аут POST не разрешает повторное создание. Неоднозначный PATCH сначала сверяется с фактическим составом WB; новый перенос вслепую запрещён.

Если WB вернул полный состав, восстанавливаются `FbsSupplyPlan`, ссылка на поставку в задачах/связях и запись аудита. Записи остатков, КИЗ, коробов, резервов, количества и статуса заявки не меняются. Отмена покупателя не вызывает повторное включение товара.

Используются те же advisory locks по клиенту/кабинету/заказу, что у ручной сборки. P2034 повторяет только откатившуюся транзакцию записи плана — никогда весь блок с запросами WB. Предпросмотр не создаёт даже контрольных записей.

Ограничение: поиск кандидатов использует сохранённый отчёт запуска с `groups[].requestNumber/error`. Аварийное завершение процесса до сохранения отчёта RUNNING не восстанавливается этим изменением. Неоднозначный POST требует сверки созданной поставки и привязки подтверждённого номера; автоматическое угадывание исключено.

## Проверка

`test/auto-assembly-recovery.spec.ts`: воспроизведение дефекта через настоящий `AutoAssemblyService.run` (падает до подключения восстановления); сохранность резерва; подтверждённая существующая поставка; неоднозначные POST/PATCH; чужой клиент/заказ; начатый отбор; отмена; исключённый склад; повтор транзакции БД; выключенный флаг; повторный запуск.

Команды из `apps/api`: `node node_modules/vitest/vitest.mjs run`, `node ../../node_modules/typescript/bin/tsc -p tsconfig.json --noEmit`.

## Публикация

Не заменять целиком production-файлы из этой ветки: исходная рабочая линия и развёрнутый runtime расходятся. В выпуск входят новый модуль и точечное подключение восстановления в `AutoAssemblyService.run`; остальные изменения live-файла должны сохраниться. Требуются сравнение baseline/candidate, проверка runtime-метода и тесты на собранном кандидате. Изменения stock/print/Telegram/TSD для этого выпуска не нужны.
