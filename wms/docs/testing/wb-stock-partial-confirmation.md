# Повтор неподтверждённых остатков WB

## Проблема

При отсутствии размера в ответе WB `selectKnownWbStockTargets` исключает его со всех складов. Остальные позиции синхронизируются успешно, и существующая очередь ранее помечала все исходные события как обработанные. Предупреждение в журнале не сохраняло задание на повтор.

## Изменение

`selectKnownWbStockTargets` сообщает текущему обработчику срочной очереди идентификаторы неподтверждённых SKU. После успешной обработки остальных подключений `WbStockSyncWorker.tick` в одной транзакции сохраняет новое событие только для пропущенных SKU, закрывает только прочитанные исходные события и сохраняет предупреждение. При неизвестном SKU сохраняется повтор по всему клиенту.

Новые бизнес-события, появившиеся во время обработки, остаются незакрытыми. При транспортной ошибке сохраняется весь первоначальный набор: последующие подключения могли ещё не проверяться. Повтор строит свежий план и заново читает WB; уже подтверждённые количества не отправляются повторно, если фактический остаток совпадает с новым планом.

Повторы используют существующую задержку: первая попытка через 5 секунд после результата, затем увеличение до 5 минут. Это не обещание мгновенного подтверждения WB. Отсутствующий на WB размер не считается нулём и автоматически не создаётся.

## Совместимость и состав

Изменены только два опубликованных модуля: `wb-stock-sync-queue.ts` и `wb-stock-safe-publication.ts`. Обработчик marketplace-connections, схема, триггеры, настройки резерва, распределение, биллинг и исправление маркировки не меняются. Поведение включено только в контексте действующей срочной очереди с `WMS_WB_URGENT_STOCK_SYNC=true`.

Ветка основана на текущей рабочей ветке `fix/historical-packing-client-free-stock`. Она не содержит файлов уже опубликованной очереди из PR 232, поэтому они добавлены из проверенной серверной базы. При интеграции с веткой, содержащей PR 232, следует применять только дельту к этим двум модулям. Полное слияние старых веток не выполнялось. Дельта и исходные хеши сохраняются в артефактах `work/wb-urgent-reservation-audit`.

## Проверки

- Новый тест до исправления воспроизводит ошибочное `PROCESSED` при неизвестном размере WB.
- Частичное подтверждение, отсутствие SKU, несколько складов, изоляция ручного предпросмотра.
- Потерянное подтверждение: повтор отправляет только неподтверждённую часть.
- Ручное повышение остатка на WB уменьшается до свежего нулевого плана WMS.
- Реальная PostgreSQL: повтор после перезапуска, новое конкурентное событие, откат при ошибке записи, потеря аренды задания.
- Тестовая БД: только отдельная `wb_urgent_retry_tests` на локальном порту 55469. Производственные запросы в тестах не выполняются.

- Локальная компиляция TypeScript прошла.
- Полный API-прогон: 2801 успешно, 2 ошибки существующего набора `fbs-print-billing-outbox.integration.spec.ts`, 3 пропущены. Повтор всего упавшего набора: 7/7 успешно. Поэтому полный прогон не обозначается как прошедший без повторов.
- Из новых проверок: 8 модульных и 3 PostgreSQL; также 7 существующих проверок очереди прошли.
- Отдельная проверка замены размера и закрытия складских остатков: 29/29.
- Кандидат из двух модулей скомпилирован поверх текущего серверного образа, без запуска рабочего приложения. В изолированном контейнере без сети: 26 проверок успешно, 7 интеграционных пропущены из-за отсутствия БД (они отдельно проверены локально).
- Два теста из текущего набора физической переклейки не проходят как на кандидате, так и на неизменённом серверном образе с теми же тестовыми файлами; новых ошибок относительно этой базы не выявлено. Это ограничение сравнения, а не основание заявлять, что все серверные проверки зелёные.
- Серверный образ, настройки, рабочие остатки и WB при проверках не изменялись.

Проданная ВМС не обновляется. В общих модулях новое поведение ограничено включённым флагом срочной очереди и её контекстом; без них сохраняется прежнее поведение.
