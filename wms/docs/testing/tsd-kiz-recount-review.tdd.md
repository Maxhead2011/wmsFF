# Полная сверка КИЗов при перемещении: WMSFF2207

Дата: 2026-09-07. Ветка: `fix/tsd-kiz-recount-review`, создана от `f22756f`
(`fix/tsd-physical-stock-reconciliation`). Производство и данные клиентов не изменялись.
План основан на подтверждённом запросе Константина автоматизировать повторяющиеся
ошибки перемещения физически имеющихся товаров.

## Пользовательский сценарий

1. В Logoff ТСД открыть «Короб → бокс», сканировать источник и ШК товара.
2. При необходимости нажать «Сверить КИЗы этого товара».
3. Сканировать **все** физические КИЗы выбранного ШК в исходном коробе, включая
   ранее неудачно отсканированную единицу. Другие товары короба не пересчитываются.
4. Нажать «Все КИЗы этого товара отсканированы» и подтвердить полный пересчёт.
5. WMS выполняет предварительную проверку. Если число сканов равно AVAILABLE,
   нет конфликтующей принадлежности, резервов или истории сборки/отгрузки/печати,
   показывает количество старых привязок и новых регистраций.
6. Нажать «Подтвердить сверку». Старые отсутствующие AVAILABLE-привязки получают
   `boxId=null, status=BLOCKED`; историческая запись и stockMovementId сохраняются.
   Новые КИЗы регистрируются за исходным коробом. Уже правильные не изменяются.
   При равном количестве числовой остаток не меняется. Продолжить обычное перемещение,
   заново сканируя ШК и КИЗ.
7. Для обычного сотрудника при расхождении количества/принадлежности/истории создаётся
   `TsdOperation(operationType=tsd_stock_recount,status=NEEDS_REVIEW)`. В WMS:
   история ТСД → «Спорные сверки КИЗов». Доступна также существующая очередь разбора.
   Видны сотрудник, короб, ШК, фактический список и причина. Автоматическое применение
   числовой инвентаризации для этого типа запрещено; существующее отклонение работает.
8. **Администратор решает на ТСД**, без очереди менеджера: видит количество до/после,
   подтверждает полное физическое наличие. Разница проводится как INVENTORY_ADJUSTMENT
   вместе с КИЗами и аудитом. Архивный, но не удалённый источник возвращается в active.
9. Если КИЗ принадлежит незавершённой сборке, предлагается административное снятие
   привязки. Перед освобождением читаются актуальные статус и метаданные WB;
   допускается только `confirm/waiting`, чужие метаданные не удаляются. Передача КИЗа
   в API не считается физической отгрузкой. Завершённая отгрузка и её история защищены.
10. Отобранный PACKING возвращается через существующий журнал резервирования,
    затем проводится абсолютный физический пересчёт — без второго слепого увеличения.
    Сохраняются заказы и номера заявок, снимается ровно соответствующая единица
    выбора короба, отменяются непечатанные задания старой наклейки. Старые стикеры
    освобождённых сборок не использовать. Остальные сборки не сбрасываются.
11. Автоматически обновляются маршруты затронутых открытых FBS-заявок того же клиента,
    филиала и SKU, в том числе ожидавших товар без назначенного короба. Повтор после сбоя маршрутов
    не повторяет пересчёт или возврат товара.
12. Подтверждение сохраняется на устройстве. При сбое доступен повтор, а для ещё
    не применённой административной сверки — «Отменить незавершённую сверку».
    Отмена не меняет остатки: только удерживаемые этой сверкой задания переходят
    в RESCAN_REQUIRED/PENDING для повторной проверки КИЗ/WB. После отмены нужен
    новый полный физический скан. Применённая сверка не откатывается кнопкой отмены.

## Границы и риски

- Общий флаг с первым этапом: `WMS_TSD_PHYSICAL_STOCK_RECONCILIATION_ENABLED=true`.
  По умолчанию отключён. API повторно проверяет флаг, роль сотрудника, клиента,
  филиал, блокировку инвентаризации. CLIENT запрещён.
- Только явный источник и выбранный товар; обычная FBS-сборка и автоматический поиск
  источника не меняются. Административное освобождение — отдельный, явно подтверждаемый путь.
- Android-экран уже ограничен `BuildConfig.FLAVOR=logoff`. FFULHAB не публиковался;
  applicationId, URL, подписи, Gradle-настройки и версия APK не менялись.
- Нулевой остаток восстанавливается по отдельной политике первого этапа при
  перемещении **одной** безопасной единицы. Полный пересчёт количества разрешён
  только после явного подтверждения администратора; завершённая отгрузка не возвращается.
- Старые и новые КИЗы проверяются по всем клиентам, вариантам представления и
  историям. Неизвестность, неоднозначность и недоступность истории не разрешают запись.
- Snapshot сравнивается внутри Serializable; повторная проверка и изменение
  привязок/аудит атомарны. Повтор подтверждения привязан к пользователю, устройству,
  филиалу, коробу, ШК, физическим идентификаторам и snapshot.
- Android сохраняет неопределённое подтверждение до отправки, восстанавливает
  после перезапуска, блокирует отмену/другой короб до получения результата.
- Список ограничен 200 единицами одного SKU и 20 связанными незавершёнными WB-заказами.
  Несовпадающее количество не корректируется молча. Пустой список не подтверждает списание.
- PREPARED/APPLIED/DONE/ABORTED сохраняются в AuditLog. ADMIN_RECOUNT_PENDING удерживает
  только согласованные задания. Одновременные подтверждения сериализуются блокировкой
  строки аудита до обмена с WB. Локальный пересчёт и освобождение — одна Serializable
  транзакция; внешние вызовы WB не являются частью транзакции WB. При откате их результат
  перепроверяется, отсутствующий КИЗ повторно не удаляется. История печати не удаляется:
  исключение действует только для освобождённых заданий внутри этой же транзакции.
- Если состав изменился во время проверки, старое число не записывается. Администратор
  может отменить незавершённую сверку на ТСД и выполнить новый физический пересчёт.
