# Сборка ФБС по номерам заказов

Опубликовано 11.10.2026 через PR561 и PR562 в `feature/wb-print-check`.
Функция включена только в нашей WMS. Проданная WMS не затронута.

## Работа пользователя

В «Сервисе» → «Сборка ФБС по номерам» администратор или собственник выбирает клиента,
кабинет WB и филиал сборки, вставляет номера заказов и запускает проверку.
Таблица показывает товар и размер, исходную поставку WB, свободный остаток, короб и
палет-сорт. После выбора короба для каждого заказа создаётся одна обычная заявка
«В работе» с резервами и стандартным маршрутом ФБС на ТСД. Две разные поставки WB
сохраняются раздельно в связях заказов. Фактический отбор и работа с КИЗ остаются в
существующем процессе ТСД.

Первая версия: 1–100 разных номеров, один кабинет WB, заказы последних 30 дней,
статусы `confirm/waiting`, открытые поставки, одна единица на заказ. Карточка WMS
определяется по точному однозначному штрихкоду. Подмена SKU и переклейка не поддержаны.
Заказы с существующей связью заявки, начатой работой, сканами, отбором или отгрузкой
блокируются. Можно использовать незапущенную AUTO-задачу из другого филиала.

## Надёжность и доступ

- API включается только `WMS_FBS_MANUAL_ASSEMBLY_ENABLED=true`; по умолчанию выключен.
  Вкладка требует `VITE_FBS_MANUAL_ASSEMBLY_ENABLED=true` при сборке web. Оба флага
  предназначены только для нашей WMS. Сервер дополнительно проверяет ADMIN/OWNER,
  `clients:write`, доступ к клиенту и запись в выбранном филиале; demo запрещён.
- Все запросы к WB только читают данные через общий ограничитель запросов. Проверяется
  принадлежность заказа поставке. Ни поставки, ни статусы WB этот механизм не меняет.
- Используются действующие политики приёмки, согласования и резервов. Запрет ФБС
  не обходится; один остаток не выделяется повторно двум заказам.
- Предварительная проверка не резервирует товар. Токен действует 10 минут, привязан
  к пользователю, кабинету, филиалу и снимку данных. Перед созданием WB читается заново,
  а локальные данные проверяются в SERIALIZABLE-транзакции с блокировками выбранных
  коробов, остатков и задач. Изменившиеся данные требуют новой проверки.
- Заявка, позиции, задачи, связи заказов, событие, аудит и результат токена сохраняются
  атомарно. Повтор того же токена/выбора возвращает сохранённый номер, в том числе
  после потери ответа. Исходные AUTO-задачи сохраняются в аудите. Новая миграция не нужна:
  журнал использует `SystemSetting`, ключи `fbs.manual.preview.v1:*`.
- Удалять использованные токены без отдельной политики хранения нельзя: они обеспечивают
  восстановление результата. Автоматическая очистка журнала в первой версии отсутствует.

этими тестами не используется. `test/fbs-manual-assembly.integration.spec.ts`
создаёт только уникальные тестовые записи в выделенной БД.

Браузер: Vite на localhost:5187, затем
`node test/fbs-manual-assembly-browser.cjs` из `apps/web`; при необходимости задать
`PLAYWRIGHT_MODULE` и `QA_URL`. Используются синтетические HTTP-ответы.
