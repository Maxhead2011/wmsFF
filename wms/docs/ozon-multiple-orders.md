# Одна сборка WMS — несколько заявок Ozon

В «ФБО → Ozon → Файл клиента — единая сборка» откройте
«Поставка и грузоместа Ozon» и добавьте каждую ссылку из кабинета Ozon.
Добавление сохраняет предыдущие заявки, общий спрос, отбор и резервы.
Один кабинет на сборку; каждая заявка Ozon принадлежит только одной сборке WMS.

Сопоставление направления содержит номер заявки и конкретный supply ID,
поэтому одинаковые названия кластеров не служат идентификаторами.
Сверка сравнивает количества каждого ШК по каждому направлению.
Данные файла не заменяются планом Ozon. Остаток не добавляется в заявку.

После общего отбора товар упаковывается в короба по направлениям.
Передача доступна после упаковки, закрытия и проверки всех коробов.
Статусы отправки и этикетки остаются отдельными для каждой поставки.
Уже начатые запросы повторно не отправляются; неопределённый результат требует
сверки. После начала передачи изменение привязки и упаковки блокируется.

Совместимость: прежний одиночный JSON читается как список из одной заявки.
Аддитивная таблица OzonFboOrderBinding переносит существующую уникальную
привязку и обеспечивает уникальность дополнительных заявок. Старое поле сохранено.
WMS_OZON_FBO_IMPORT_ENABLED остаётся прежним; проданная WMS вне выпуска.

Проверенная заявка №1861: четыре заявки кабинета 133456539, 133455507,
133455289, 133455152. 393 единицы, 11 направлений; на 09.10.2026 все строки
по ШК и количеству совпали. Это сверка плана, не подтверждение физической сборки.

Тесты: ozon-multiple-orders.spec.ts, ozon-supply.integration.spec.ts,
ozon-multiple-orders-browser.cjs. Новый тест воспроизводит замену первой
заявки старым bind; исправление сохраняет обе. PostgreSQL проверяет
конкурентную привязку и однократную отправку. Браузер проверяет готовый JS-граф.
Runtime меняет только два Ozon-модуля API и веб-граф; APK222 и агент печати сохранены.
Клиентский шаблон Excel будет согласован отдельно.
