# Статистика обработки и приёмки заказов

Раздел «Склад и операции → Статистика», workspace `operations-statistics`.

## Контракт — 13.09.2026

- Единица: один связанный с заявкой WMS заказ; ключ — маркетплейс + подключение + номер. Не количество вещей и не повторных сборок.
- Начало WB: `createdAt` из `/api/v3/orders`. Для истории допустим сохранённый исходный `orderPlacedAt` либо точное соответствующее событие SALE. Импорт в WMS и время сборки не заменяют дату заказа.
- Конец WB: `scanDt` текущей поставки из `/api/v3/supplies/{supplyId}`. Связь — ответ WB для конкретного заказа, не SKU/название. Это **скан поставки**, не индивидуальный скан каждой вещи.
- `sentToWbAt`, `handedOverAt`, `closedAt`, сборка, печать и плановая отгрузка в новом расчёте не используются.
- Зоны: [0,14), [14,18), [18,24), [24,48), [48,+∞) часов. Процент = заказы зоны / заказы с рассчитанным сроком до скана. Без знаменателя — прочерк, не 0%.
- Отменённые и требующие повторной отгрузки заказы исключены из временных зон. Будущие/обратные даты — «Нет данных о времени».
- Период — по созданию заказа, дни включительно, Москва UTC+3, максимум 93 дня. Заказ без даты нельзя отнести к периоду: отдельный счётчик всей доступной истории.
- **Ozon:** подтверждённый источник даты создания покупателем и фактического скана пока не подключён. `in_process_at` и `delivering_date` не подменяют эти события. Ограничение видно в интерфейсе; обновление работает с WB.

## Приёмка — отдельный показатель

Скан поставки НЕ подтверждает приёмку всех её заказов.

- WB `sorted`, `sold`, `ready_for_pickup` — подтверждённое дальнейшее прохождение заказа у WB; это статус, не точная дата приёмки.
- WB `waiting` — ожидает приёмки, даже если поставка уже просканирована.
- Заказ в `/api/v3/supplies/orders/reshipment` — «Довезти», даже при старом успешном статусе.
- Отмена — отдельно; остальные/отсутствующие статусы — неизвестны.
- Ядро расчёта поддерживает приоритет индивидуального скана, но источник такого времени ещё не подключён. Момент обнаружения статуса при опросе не является временем скана.

Срок по поставке может быть рассчитан, а приёмка заказа ещё ожидаться. Интерфейс показывает обе величины, не объединяя их в «100% отгружено».

## Область обслуживания LOGOFF

Только активные подключения и обслуживаемые склады: CENTRAL → центральный филиал подключения; BRANCH → явно заданный филиал; EXCLUDED → исключается даже при старой заявке и совпадении со складом по умолчанию. Без правила — только выбранный склад подключения либо включённая автоматическая маршрутизация.

Название LOGOFF не является фильтром. Неизвестный склад не доказывает обслуживание. Филиалы без обслуживаемых складов скрыты. Обработанные заказы группируются по филиалу заявки WMS, затем по кабинету/складу продавца. Сохраняются ограничения клиентов и филиалов пользователя; CLIENT/demo запрещены.

## Обновление и полнота

GET отчёта читает только WMS; таблица обновляется раз в минуту при видимой вкладке. «Получить даты и статусы WB» запускает отдельную фоновую проверку периода. POST создаёт задачу; GET прогресса доступен только тому же пользователю с тем же набором областей доступа.

Запросы используют общий существующий лимитер WB и фоновый приоритет, уступая интерактивной работе ТСД. Период делится на окна до 30 дней, страницы проходятся до конца. Проверяются кабинет, склад обслуживания и доступная заявка WMS. Запись — только в `OperationsStatisticsFact`, без изменений заказов, резервов, КИЗов, остатков и статусов маркетплейса.

Частичные ответы, HTTP-ошибки, зацикленная пагинация, недоступные сканы и истечение времени не считаются полным обновлением. Повтор — upsert по уникальному ключу заказа. При смене поставки старый скан не переносится.

Видны самая свежая и самая старая проверки включённых заказов, число ещё не проверенных новым механизмом и ошибки обновления. Успешный запрос не гарантирует сохранность всей старой истории WB. Отсутствующие даты не восстанавливаются предположениями.

Прогресс хранится в памяти одного процесса API до часа (до 20 записей). Одна задача одновременно в процессе; новый запуск не чаще минуты; лимит 10 минут на задачу, 30 секунд на запрос, 100 страниц на окно. После перезапуска API клиенту предлагается повтор, сохранённые факты остаются. Для нескольких реплик API потребуется общий диспетчер задач; текущий механизм предназначен для однопроцессного развёртывания LOGOFF.

## Файлы и выпуск

- `apps/api/src/modules/operations-statistics/`: область, агрегация, правила приёмки, обновление, DTO, контроллер, тесты.
- `apps/api/prisma/migrations/20260913000000_statistics_acceptance_facts/`: изолированная таблица, без переписывания истории.
- `apps/web/src/components/operations-statistics/`, `apps/web/src/lib/api.ts`: интерфейс и контракт.
- `marketplace-connections.service.ts`: экспорт прежнего HTTP-helper для общего лимитера; логика сборки не меняется.
- Реестр внутренних API: три маршрута статистики; доступ `stock:read` плюс область клиента/филиала.

Перед выпуском: резервная копия, новая миграция, Prisma generate, API, затем web. Проданное окружение не обновлять. Локальный checkout не равен production: сохранить независимые серверные изменения при подготовке релиза.

Источник WB: https://dev.wildberries.ru/en/docs/openapi/orders-fbs?locale=ru — заказы, статусы, повторная отгрузка, информация о поставке.
