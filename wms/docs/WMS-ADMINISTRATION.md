# WMS LOGOFF — администрирование владельца

## 1. Защищённый раздел

«Администрирование» доступно не всем пользователям с ролью OWNER или ADMIN. Сервер проверяет отдельный список `administration.ownerUserIds`. Отсутствие плитки и ответ HTTP 403 для постороннего пользователя являются нормальным поведением.

В production в список должен входить только персональный ID владельца. Не используйте общий логин.

## 2. Центр управления

Главная вкладка показывает:

- количество пользователей, клиентов, SKU, коробов и заявок;
- активные подключения маркетплейсов;
- незавершённые решения инвентаризации;
- uptime, память и версию Node.js API;
- текущую политику коробов;
- состояние ИИ-провайдера;
- быстрые переходы к редакторам данных.

Сущности редактируются через профильные модули. Это сохраняет бизнес-проверки, историю движений и аудит. Прямое редактирование базы не является штатным способом.

## 3. Настройки

Настройки хранятся в `SystemSetting`. Для каждого изменения обязательна причина. API проверяет тип, диапазон и допустимые значения.

### Политика номеров коробов

Ключ: `warehouse.boxCodePolicy`.

Поля:

- `primaryPrefix` — основной префикс новых коробов;
- `allowedPrefixes` — все префиксы, разрешённые при сканировании;
- `receiptPrefix` — основа номера онлайн-приёмки перед датой;
- `balancePrefix` — префикс служебных балансировочных коробов;
- `autoCorrections` — безопасные исправления известных опечаток.

Пример:

```json
{
  "primaryPrefix": "LOGOFF_",
  "allowedPrefixes": ["LOGOFF_", "FFL_"],
  "receiptPrefix": "LOGOFF_LKB",
  "balancePrefix": "LOGOFF_BAL",
  "autoCorrections": {
    "FL_": "FFL_"
  }
}
```

Старый префикс нельзя удалять из разрешённых, пока на складе существуют активные короба с ним. Смена префикса не переименовывает историю и существующие короба.

### Обновление экранов

Слишком короткий интервал создаёт лишнюю нагрузку. Рекомендуется 5–15 секунд для оперативных экранов и тихое обновление без сброса прокрутки. Допустимый сервером диапазон: 2–300 секунд.

### Диагностика маркетплейсов

Настройка определяет интервал и уведомление владельца. Ручная проверка всегда безопасна для данных: она вызывает только методы чтения.

## 4. Видимость интерфейса

Для пользователя можно скрыть любой обычный workspace. Это не изменяет роли и не выдаёт новых разрешений. Состояние «по ролям пользователя» означает отсутствие персонального запрета.

Сам раздел «Администрирование» нельзя включить матрицей видимости: для него требуется присутствие в owner allowlist.

## 5. Диагностика WB/Ozon

Для WB проверяются:

1. формат и срок жизни JWT, если ключ является JWT;
2. получение доступных складов;
3. получение новых FBS-заказов;
4. получение истории заказов;
5. существование выбранного `fbsWarehouseId`.

Для Ozon проверяется `Client-Id`, `Api-Key` и метод информации о продавце.

Ключи никогда не возвращаются в веб и не записываются в аудит. В отчёте показываются только возможности, HTTP-статус, время ответа и безопасное сообщение.

## 6. ИИ-помощник

Ключ настроек: `administration.ai`.

Без `OPENAI_API_KEY` работает локальный детерминированный планировщик. Он умеет:

- подготовить и применить изменение основного префикса;
- запустить read-only диагностику WB;
- построить безопасный технический план для программного изменения.

С ключом OpenAI следует использовать актуальную модель, Structured Outputs и function calling. Ключ передаётся только через secret/environment сервера и не хранится в PostgreSQL или браузере.

Защитный цикл:

1. владелец описывает задачу;
2. помощник возвращает структурированный план;
3. WMS показывает риск, проверки и откат;
4. только allowlisted-действия становятся исполняемыми;
5. владелец вводит `ПРИМЕНИТЬ`;
6. API повторно проверяет владельца и план;
7. действие выполняется и пишется в AuditLog.

Запрещены произвольный shell, произвольный SQL, передача секретов модели и саморедактирование production-кода без сборки и тестов.

## 7. Аудит

Записываются как минимум:

- изменение настройки;
- изменение видимости;
- диагностика маркетплейсов;
- предпросмотр ИИ;
- применение ИИ-плана.

Запись содержит автора, время, объект, причину, значение до и после. Удаление аудита через веб не предусмотрено.

## 8. Управление владельцами

Изменение `administration.ownerUserIds` выполняется только техническим администратором после проверки личности и резервной копии. Безопасная процедура:

1. найти точный UUID пользователя;
2. добавить новый UUID, не удаляя действующий;
3. проверить новый логин и HTTP 200 `/administration/overview`;
4. только после этого удалить старый UUID;
5. записать действие в отдельный журнал работ.

## 9. Опасные операции

Перед массовыми изменениями:

1. сделать дампы обеих PostgreSQL баз;
2. сохранить Redis;
3. сохранить исходники и конфигурацию;
4. проверить SHA-256;
5. проверить чтение дампа через `pg_restore --list`;
6. выполнить preview;
7. применить на ограниченной выборке;
8. проверить остатки, движения и биллинг.

Нельзя напрямую менять остаток без парного движения и записи причины.
