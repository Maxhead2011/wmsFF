# Общий остаток WB/Ozon — реализация в работе

Ветка `feature/multishop-shared-stock`, цель PR — `feature/wb-print-check`.
Этот документ не подтверждает выпуск или включение автоматической отправки.
Опубликованный редактор PR689 пока сохраняет только черновики.

## Реализовано локально

- `multishop-stock-plan.ts`: `ALLOCATED` (по долям) и `SHARED` (одинаковый
  доступный остаток каждому магазину). Страховой запас вычитается один раз;
  после него применяется порог последних единиц и приоритет магазина.
- Старые настройки без режима сохраняют распределение по долям, без страхового
  запаса. Неверный режим, отрицательное/дробное количество отклоняются.
- `multishop-stock-groups.service.ts`: сохранение режима и запаса в прежней
  транзакции с версией и аудитом. Сохранение не включает отправку.
- `MultishopStockGroupsView.tsx`: выбор режима, запас, пояснения; при возврате
  из общего режима прежние доли сохраняются.
- `multishop-stock-reservations.ts`: чистый расчёт по уже нормализованному
  снимку. Заказ и связанная заявка считаются одной потребностью. Повтор одного
  заказа не увеличивает резерв; одинаковые номера в разных кабинетах различны.
- `multishop-stock-publication.ts`: режим сверяется с актуальной конфигурацией
  перед каждым запросом. Старое задание не может само разрешить общий режим.

Пример: AVAILABLE=20, неотобранный заказ=1 → свободно=19. После физического
отбора AVAILABLE=19, остаток потребности=0 → свободно всё ещё 19. Сам заказ не
создаёт складского списания. Нормализатор обязан подтверждать физический отбор
движениями, а не количеством сканирований.

## Что ещё необходимо для включения

1. Рабочий снимок данных: клиент, физический склад, подтверждённые приёмки,
   разрешённое направление, канонический SKU, все активные WB/Ozon-заказы
   и заявки ФБО. Существующий `wbReservationQuantities` выбирает задания WB;
   `FbsStockMonitoringService.ingestOrders` также фильтрует кабинеты WB.
   Их нельзя использовать как полный реестр всех маркетплейсов.
2. Полные многотоварные отправления Ozon: каждая строка связана с SKU, вычтен
   фактический отбор, учтены отмены. Неполный ответ, неизвестная связь или
   устаревшие данные должны блокировать увеличение, а не означать нулевой резерв.
3. Постоянная очередь и единый контроль отправителей: блокировка по физическому
   SKU, версия снимка, предыдущие и новые назначения, восстановление после сбоя.
   Нельзя подключать worker без защиты существующих ручных и фоновых WB-записей.
4. Проверенный транспорт Ozon: реальные контракты чтения и записи, отличие
   свободного количества от собственного резерва площадки, ограничения частоты,
   повторное чтение после неопределённого результата. В существующем сервисе
   нет готового отправителя остатков Ozon.
5. Явное включение после предпросмотра; интеграционные проверки конкурентных
   заказов, отмены, частичного отбора, смены группы, удаления магазина и
   перезапуска worker. Положительный ACK не равен подтверждённому остатку.
6. Свежая проверка production и точечный overlay: текущая документация уже
   содержит PR691 Lamoda. Старые артефакты PR689 не являются базой выпуска.

Чистый алгоритм и изолированные UI-тесты не доказывают правильность рабочего
снимка, внешних записей или поведения одновременно работающих отправителей.
Проданная ВМС, физические остатки и действующие настройки клиентов не менялись.

## Проверки

`multishop-shared-stock.spec.ts`, `multishop-stock-reservations.spec.ts`,
`multishop-stock-plan.spec.ts`, `multishop-stock-groups.spec.ts`,
`multishop-stock-publication.spec.ts`; браузерный сценарий
`wms/scripts/tests/multishop-groups-browser.cjs` проверяет сохранение/перезагрузку
общего режима и страхового запаса, возврат долей, конфликт версий и мобильную ширину.
API браузерного сценария изолирован; внешние изменения остатков равны нулю.
