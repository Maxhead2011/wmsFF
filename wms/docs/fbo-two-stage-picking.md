# Двухэтапная сборка ФБО

## Раздельные маршруты отбора LOGOFF (опубликовано PR485, 05.10.2026)

В открытой сборке ФБО после начала отбора доступны два пункта:

- **Сборка целых коробов** — строки оставшегося серверного маршрута с `wholeBox=true`,
  без требования пересчёта, за исключением стационарных боксов `FFL_LKBBOX_` при
  включённом режиме повторного использования. Короб подтверждается существующей
  кнопкой с вводом фактического количества; поштучный отбор в этом пункте закрыт.
- **Частичный отбор** — остальные строки того же плана: ШК товара и КИЗ по прежним
  правилам. Весь товар из стационарного бокса по-прежнему можно забрать существующей
  кнопкой, сам бокс остаётся на стеллаже.

Список паллет, коробов и проверка сканов используют один выбранный маршрут.
Счётчики пунктов отражают оставшийся план, а общий прогресс — всю заявку.
«Завершить отбор» доступно только после отбора полного количества по заявке.
«К выбору отбора» очищает локальный адрес и перечитывает маршрут без изменения
остатков. При незавершённой паре ШК/КИЗ или неизвестном результате отправки
переключение заблокировано. Сохранённая операция повторяется с исходным UUID.
Пересчёт маршрута может изменить категорию короба; тогда старый выбранный адрес
сбрасывается. Уже отобранные и упакованные единицы не перераспределяются.

Изоляция: только `BuildConfig.FLAVOR == "logoff"`, экран отбора. Упаковка, FBS,
серверная схема, API и flavours `ffullhab`/`platform` сохраняют прежнее поведение.
Онлайн-сборка в браузере этим изменением не затрагивается.
Тесты: `FboPickingModeTest`, `FboPickingRouteTest`, прежние FBO-сценарии и полный
набор Android-тестов трёх flavours. PR485 объединён в `feature/wb-print-check`; опубликован LOGOFF APK217.
Локально 05.10.2026: LOGOFF 226, FFULLHAB 226, Platform 226 — без ошибок;
`assembleLogoffDebug` и `git diff --check` прошли. Первые три регрессионных сценария
нового меню воспроизвели отсутствие разделения до изменения. Проверка на физическом
ТСД пока не выполнялась. Публикация APK217 и публичные контрольные суммы проверены.

## Исходное описание двухэтапной сборки

Изменение для нашей ВМС, ветка `feature/fbo-two-stage-picking`; предполагаемая база PR — `fix/fbs-transfer-started-at`.

## Действия сборщика

1. Открыть заявку в ТСД или онлайн-сборке и нажать «Начать отбор».
2. Сканировать паллет: появится список нужных коробов именно на нём. Сканировать исходный короб. Короб без паллета можно сканировать сразу.
3. Если весь однородный короб нужен заявке и состав КИЗ согласован с остатком, доступна кнопка «Короб забран целиком». Иначе повторять ШК товара → КИЗ, следя за оставшимся количеством. Для явно немаркируемых единиц КИЗ не придумывается; фактические марки учитываются даже при незаполненном флаге маркировки SKU.
4. После полного отбора перейти к упаковке. Сканировать ШК пустого короба, затем ШК → КИЗ каждой отдельной отобранной единицы и нажать «Закрыть короб». Целый отобранный короб добавляется сканом его ШК. Случайно открытый пустой короб можно отложить.
5. После раскладки всех единиц и закрытия всех коробов нажать «Короба разобраны».
6. Сканировать каждый короб поставки, включая взятые целиком. После последнего подтверждения нажать «Завершить проверку и сформировать файл WB». Загрузится XLSX; повторное скачивание остаётся доступным.

## Учёт и восстановление

- Отбор выполняет AVAILABLE → PACKING один раз. Отдельные единицы находятся в техническом контейнере `FBO-PICK-<requestId>`; это состояние отбора, а не адрес хранения. Записываются исходный короб, сотрудник, физический КИЗ и время.
- Упаковка перемещает те же PACKING-единицы в транспортные короба. Чужой или уже вложенный КИЗ отклоняется.
- Финальная проверка сравнивает количество и конкретные КИЗ с содержимым каждого короба. После неё штатная упаковка создаёт грузоместа, начисления и SHIPPING в одной транзакции. Штатный файл WB использует эти фактические грузоместа.
- Запросы имеют сохраняемый идентификатор операции. При неизвестном результате ТСД и браузер предлагают повторить тот же запрос; он не списывает товар повторно. Неподтверждённая операция сохраняется и после перезапуска, отдельно для пользователя и заявки.
- Другой филиал/клиент, изменённый состав заявки, лишняя единица, чужой паллет, ранняя упаковка и повторное подтверждение короба отклоняются на сервере.
- Старые массовые операции не могут обходить новый отбор. Заявки с уже выполненными операциями прежней сборки автоматически не переводятся в новый режим.
- Недостача или неизвестный КИЗ требует сверки штатными средствами склада; автоматического создания остатка и подмены КИЗ нет. Отмена заявки также не возвращает отобранный товар в исходный короб. Возврат требует отдельного документированного складского действия.

## Изоляция и публикация

По умолчанию `WMS_FBO_TWO_STAGE_ENABLED=false`. Проданная ВМС продолжает старый сценарий; вход в новый Android-экран ограничен вариантом `logoff`. Новые таблицы не переписывают исторические движения и остатки.

Перед включением на нашей ВМС:

1. Зафиксировать текущие серверные образы, базу и APK; сверить параллельные изменения. Рабочий сервер содержит дополнительные изменения по сравнению с исходным checkout, поэтому нельзя заменять его целиком старой сборкой из этой ветки.
2. Применить миграцию `202609160002_fbo_two_stage`, сгенерировать Prisma Client и выпустить совместимые API/web и LOGOFF APK с новым номером версии поверх актуального приложения.
3. Только затем включить флаг, проверить план заявки №001029 и доступы сборщика. Номер версии APK определяется при выпуске, чтобы не пересечься с параллельной публикацией.
4. Не выключать флаг и не удалять таблицы при незавершённых новых сборках. При необходимости остановить новые старты и сначала сверить/завершить активные заявки.

В этой задаче рабочая заявка №001029 только прочитана. Миграция и сценарии движения проверены на отдельной локальной PostgreSQL; публикация требует согласования PR.

## Проверки

`fbo-two-stage-policy.spec.ts`: целый/смешанный короб, ограничение потребностью, несовпадение КИЗ, счётчики единиц.

`fbo-two-stage.integration.spec.ts`: реальные транзакции PostgreSQL, полный цикл и XLSX, повтор после потери ответа, параллельные ТСД, откат упаковки при ошибке начисления, доступы, паллет, отмена пустого короба, немаркируемый товар, исторические марки и защита старых путей.

`FboTwoStagePanel.spec.tsx` и `FboScanStateTest.java`: последовательность экранов, скан паллета и короба, недоступность раннего экспорта, сохранение операции после перезапуска, повтор без нового списания.

Дополнительно перед коммитом запускаются общие API/web-тесты, TypeScript-проверки, web-сборка и все Android unit test варианты с тестовой сборкой APK. Проверка на физическом ТСД и загрузка файла в кабинет WB выполняются после выпуска.
