# Склад — ткани, хранение и учёт

Опубликовано PR945, 09.11.2026. Baseline `2026-11-09-warehouse-fabric`.

В собственной WMS пункт «Склад → Ткани: хранение и учёт» открывает выбор клиента,
остатки рулонов и готовых отрезов, историю, приёмку, нарезку, корректировку и
списание рулонов. Существующий клиентский просмотр в «Кабинете» сохранён.
Новый вход проверен; «Кабинет» снова скрыт у администраторов без OWNER, клиентский просмотр сохранён.

При приёмке можно добавить новый цвет выбранной ткани клиента. Названия
нормализуются: пробелы, регистр и ё/е не создают дубликаты. Атлас и габардин
имеют разные наборы новых цветов. Старые шесть цветов и старые артикулы сохранены.

Рулоны можно принять до появления карточки маркетплейса. Позже выбирается
существующая карточка товара WMS, связанная с WB/Ozon, и точная длина отреза
(0,001–100 м). Карточки 5 м и 10 м расходуют один пул ткани/цвета. Новая
привязка записывается в `Sku.marketplacePayload.fabricRollBinding`; обновление
карточки из маркетплейса сохраняет её. Чужой клиент, другой материал,
переназначение уже распознанного SKU и новая привязка SKU с положительным
складским остатком отклоняются. Привязка не создаёт готовый остаток и сама
не включает публикацию остатков или нарезку FBS у клиента.

Цвета находятся в `fabric.catalog.v1:<clientId>`. Изменения требуют прав записи,
принадлежности клиента выбранному филиалу и актуальной версии каталога,
сериализуются блокировкой `fabric.rolls.v1:<clientId>` и записываются в аудит.
Каталог закрыт при выключенном `WMS_FBS_FABRIC_CUT_ENABLED` и в демо.
Пункт интерфейса включён только на `wms.logoff.pro`.

Исходники: `FabricWarehousePanel.tsx`, `fabric-catalog.controller.ts`,
`fabric-catalog.ts`, `fabric-fbs-availability.ts`, проекция
`fbs-fabric-reservation.ts`, сохранение привязки при синхронизации SKU.

Source/runtime parity для нашей WMS остаётся false. Полная локальная сборка не
предназначена для замены опубликованного сервера. `scripts/releases/fabric-catalog-20261109/prepare.cjs`
подготавливает точечные изменения текущих `fabric-rolls.js`,
`fabric-shipment-accounting.js`, `warehouse.module.js`, основной службы
маркетплейсов и проекции резервов; при изменении ожидаемого кода подготовка
останавливается. Дополнительно нужны собранные `fabric-catalog.js`,
`fabric-catalog.controller.js`, `fabric-fbs-availability.js` и регистрация двух
новых маршрутов в справочнике административного API. Перед публикацией нужно
снова сверить текущие образы, подготовить точечный web overlay и проверить его
полную загрузку, согласованность React entry/import map и прежние функции тканей.
Production и проданная WMS этой подготовкой не изменяются.

Проверки кандидата: API домен/контроллер/доступность/проекция/реестр — 71 тест;
веб — 610 passed, 2 skipped; воспроизведение на старом runtime и проверка
исправленного приёма/нарезки/синтаксиса списания — 4 passed; браузерный сценарий
с синтетическими API: создать цвет → принять рулон → связать отрез 5 м — passed.
Полный API прогон: 4578 passed, 177 skipped и один сбой ожидаемого числа групп
API; после обновления ожидаемого числа 37→38 весь затронутый набор прошёл.
`kiz-duplicate.integration.spec.ts` исключён: требует отдельную локальную БД и
падает при создании PrismaClient с отсутствующим URL даже в skipped-suite.
API typecheck сохраняет прежние ошибки устаревшего Prisma-клиента Lamoda и
nullable SKU в Яндекс; новых ошибок в изменённых файлах не найдено.
Typecheck веба прошёл. Физическая приёмка/ТСД и реальная синхронизация новой
карточки маркетплейса в production не выполнялись.
