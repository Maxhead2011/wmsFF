# Перенос WB без доступного остатка

Новая логика работает в обработчике «Перенести в новую поставку». Заказы без доступной единицы товара в выбранном филиале направляются в отдельную новую поставку WB с точным названием `logoff нет на складе`. Совместимые заказы объединяются в группы до 100 заказов; разные кабинеты, склады WB, габариты и трансграничные типы разделяются. Существующую поставку только по совпадению названия система не выбирает.

При смешанном выборе заказы с остатком сохраняют обычный маршрут. Для ещё не отобранного заказа из доставки разрешена попытка переноса из `complete/waiting`; окончательное решение принимает WB. WMS меняет привязку только после проверки состава новой поставки и статуса `confirm/waiting`. Отменённые, полученные и уже обрабатываемые WB заказы, закрытые заявки и заказы с физическими сканами не переносятся.

Остаток проверяется по клиенту, выбранному филиалу и физическому SKU переэтикетки. Учитываются резервы других заданий, собственный резерв и распределение доступных единиц между всеми выбранными заказами. Для коробочного хранения используются доступные короба на палетах выбранного филиала; для бескоробочного хранения резервы также ограничиваются филиалом. Проверка отражает состояние на момент подготовки переноса и не является новой физической резервацией.

## Изоляция и включение

На API нашей ВМС должны быть включены обе настройки:

```dotenv
WMS_FBS_RESHIPMENT_ENABLED=true
WMS_FBS_NO_STOCK_TRANSFER_ENABLED=true
```

На проданной ВМС `WMS_FBS_NO_STOCK_TRANSFER_ENABLED` оставляется отсутствующей или `false`. Тогда обработчик переноса вызывает прежнюю реализацию, а интерфейс не открывает перенос заказов из доставки. Миграция БД не требуется: уникальное имя записи `FbsReshipmentRun.supplyName` остаётся `WMS-RES-<UUID>`; видимое название WB выводится из сохранённого назначения операции.

Изменяются обработчики переноса/чтения FBS, проверка остатков, журнал повторной отгрузки и отображение результатов в FBS и заявках. Общие модули API и интерфейса затронуты, поэтому проверка отключённого флага и регрессионные тесты повторной отгрузки обязательны перед выпуском.

## Сбои и продолжение

- Перенос не списывает товар и не создаёт историю второго физического отбора. Нехватка оставляет существующее задание в `WAITING_STOCK`.
- Неопределённый ответ на добавление заказов восстанавливается проверкой состава уже известной поставки; повторного `PATCH` для подтверждённых заказов нет.
- Если WB создал поставку, но ответ с её ID потерян, операция остаётся в журнале. Для одинаковых публичных названий нельзя безопасно определить принадлежность пустой поставки: требуется ручная сверка ID администратором. Повторного создания или присвоения чужой поставки по имени нет.
- Пересчёт исходной заявки имеет отдельный сохраняемый этап `SOURCE_SYNC_PENDING`. Его можно продолжить в журнале после создания новой заявки, без повторного изменения WB.
- Интерфейс показывает результаты каждой группы, пропущенные заказы и незавершённые операции.

## Проверка

Регрессии добавлены в `apps/api/test/fbs-stock-transfer.spec.ts`, `fbs-stock-transfer-gateway.spec.ts`, `fbs-reshipment-service.spec.ts`, а также в тесты `FbsReshipmentPanel` и `lib/fbs-stock-transfer` интерфейса. Они используют синтетические заказы и имитацию WB; реальные заказы при локальном тестировании не переносятся.

Перед коммитом выполняются все тесты API и web, проверки TypeScript и сборка Vite.
