# Контроль наклейки Ozon после упаковки

Порядок: отбор → упаковка/закрытие коробов → SORTED → передача грузомест
из WMS → получение/наклейка этикеток → CONTROL на ТСД → завершение.
LOGOFF248: скан нашего короба выбирает его, второй скан с наклеенного стикера
передаёт targetBoxCode + barcode в существующую идемпотентную CONFIRM_BOX.
Сервер сверяет точный строковый cargo_id, ключ FboAssemblyBox.id и направление.
Флаг WMS_OZON_LABEL_CONTROL_ENABLED включается только в образе нашей API.
WB/Lamoda и проданные варианты сохраняют прежний порядок.

Сервер хранит boxLabelChecks в существующем JSON integration вместе с cargoId,
supplyId, frozenHash, временем и пользователем. Событие в истории фиксируется
в той же транзакции, что и подтверждение. Повтор operationId не дублирует событие.
FINISH требует все актуальные пары; прежний confirmedAt без пары не достаточен.
Завершённые заявки не переоткрываются. Изменение состава после отправки остаётся
запрещено; изменившееся соответствие аннулирует действительность проверки.
Сканирование подтверждает соответствие, а не физический факт приклеивания:
экран требует сканировать этикетку уже на коробе.

Также включён журнал нажатий скачивания стикеров и время истории до секунды МСК.

Проверки: API4116/web569/Android924; пропущены API156/web2, отдельный локальный
KIZ DB suite без конфигурации исключён. TypeScript, release APK248/lintVital,
точный overlay6 API/6web, проверка baseline, PostgreSQL12 с полным запуском API,
браузер6 и регрессия импорта10 с синтетическими API. Реальных отправок Ozon
для тестирования нет. Действующий runtime PR783 сохранён, sourceParityVerified=false.
